# Пакеты для Linux: deb, rpm и AppImage

Одна команда собирает три формата из одного набора файлов:

```bash
nix develop --command dj-release --linux     # пакеты + tar.gz (весь путь релиза)
nix develop --command bash scripts/linux-packages.sh --all   # только пакеты
```

| файл | для кого | размер (0.1.0) |
|---|---|---|
| `hauler-dj_0.1.0_amd64.deb` | Debian, Ubuntu и производные | 223 МБ |
| `hauler-dj-0.1.0-1.x86_64.rpm` | Fedora, openSUSE и производные | 253 МБ |
| `hauler-dj-0.1.0-x86_64.AppImage` | один файл, любой дистрибутив | 185 МБ |

Установка — обычная для формата: `dpkg -i`, `dnf install ./файл.rpm`, AppImage — `chmod +x` и запуск. Все три ставят
одно и то же дерево: `/usr/bin/{hauler-dj,dj-engine,dj-ui,dj-launcher}`, `/usr/lib/hauler-dj/`, запись в меню,
иконки и лицензии.

## Что внутри

Пакет несёт всё, что нужно программе: движок, оболочку, запускатор, библиотеки Qt (Core, Gui, Widgets, Quick,
QuickControls2, Network), плагины Qt (платформы X11 и Wayland, темы, форматы изображений, TLS), QML-модули, шрифтовой
стек и **свой загрузчик glibc**. Из системы берётся только ядро и графический драйвер.

Установленный размер — около 1,4 ГБ, потому что внутри полная среда исполнения, а не ссылки на неё. Это цена
переносимости: пакет не зависит от версии glibc, версии Qt и набора библиотек в дистрибутиве.

## Почему через загрузчик, а не через PT_INTERP

Двоичные файлы собраны в nix-оболочке, и их интерпретатор ELF указывает в `/nix/store` — каталога, которого на
чужой машине нет. Переписывать интерпретатор бессмысленно для AppImage (он монтируется в `/tmp/.mount_*`, а путь в
ELF абсолютный) и хрупко для deb. Поэтому настоящие двоичные файлы лежат в `/usr/lib/hauler-dj/bin`, а в
`/usr/bin` лежат крошечные обёртки:

```sh
exec /usr/lib/hauler-dj/ld-linux-x86-64.so.2 --library-path /usr/lib/hauler-dj \
     /usr/lib/hauler-dj/bin/dj-engine "$@"
```

Загрузчику, которому программу передали аргументом, PT_INTERP безразличен: он уже работает. Запускатор при этом
остаётся настоящим двоичным файлом в `/usr/bin` — он ищет движок и оболочку рядом с собой и находит эти обёртки.

Из двоичных файлов и библиотек набора при сборке вычищается `RPATH`: в нём записаны пути сборочной машины, и
`DT_RPATH` старше `LD_LIBRARY_PATH`, то есть на чужой системе поиск начинался бы с несуществующих каталогов.

## Что проверяется при сборке

Сборка не заканчивается словом «готово»:

1. **Все связанные библиотеки — из набора.** Загрузчик перечисляет, откуда он взял каждую; любая строка вне набора
   означает, что на чужой машине библиотеки не будет.
2. **Оболочка запускается из набора** с `QT_DEBUG_PLUGINS=1` и доходит до своих строк, а все загруженные плагины
   лежат внутри набора. Это проверяет Qt-плагины, QML и шрифты — то, что `ldd` не видит.
3. **Подпись squashfs в AppImage** стоит сразу за рантаймом (по смещению размера рантайма) — образ смонтируется, а
   не рассыплется.
4. **deb и rpm проверяются своими инструментами** — `dpkg-deb -I`, `rpm -qip`: имя, версия, лицензия, список файлов.

## Чего эта сборка не доказывает

- **AppImage не запускался здесь.** Его рантайм — обычный ELF под FHS-загрузчик `/lib64/ld-linux-x86-64.so.2`,
  которого на NixOS нет (ровно поэтому существует `appimage-run`). Образ собран и его содержимое проверено, но
  запуск нужно подтвердить на обычном дистрибутиве.
- **deb и rpm не ставились на живые Debian и Fedora.** Установка — обычная для формата, дерево файлов проверено,
  но `dpkg -i` на чистой машине — за владельцем.
- **На NixOS эти пакеты не нужны**: там `nix run github:UncleAndy/hauler-dj-platform`.

## Инструменты

Сборке нужны `dpkg`, `rpm`, `squashfsTools`, `patchelf` и `curl` (рантайм AppImage скачивается один раз в
`~/.cache/appimage-runtime`); всё это уже в оболочке разработчика. `rpmbuild` запускает свои шаги через `/bin/sh`,
которого в контейнере нет, — для него подкладывается статический busybox через `bwrap` с ядром хоста.
