# RT-контракт аудиопотока

Контракт, на который опираются A01…A04. Правила ниже не декларация: каждое закрыто
исполняемой проверкой в `crates/dj-audio-core/tests/` и `dj-testkit::rt`, зелёной в
`bash scripts/check.sh`. Свидетельства — `docs/qa/evidence/A01/`.

## Границы

1. **Audio callback.** Фиксированный блок, только заранее выделенные буферы. Запрещены:
   heap allocation, mutex/wait, файловый и сетевой I/O, логирование, вызовы Qt, ML, syscall,
   способный блокировать, `unwrap`/`panic` на пути данных.
2. **Состояние меняется только командами.** UI и контроллеры не пишут в DSP-структуры напрямую
   (DJP-ARCH-001). Критические команды (`Play`, `Stop`, `Load`, `Unplug`) не вытесняются потоком
   регуляторов (DJP-ARCH-002, -003).
3. **Снимки состояния** публикуются без блокировки аудио: `revision`, `audio_clock_samples`,
   `epoch`. Устаревший снимок не является подтверждением команды (DJP-ARCH-004).
4. **Инициализация и замена графа** — вне критического потока, на границе блока либо в заранее
   выделенной структуре (DJP-ARCH-005).
5. **Время.** `source_frame` и `audio_clock_samples` — разные шкалы; переход всегда явный, через
   `timebase` и `sample_rate` (DJP-DATA-002).

## Как это проверяется

| Правило | Проверка | Задача |
|---|---|---|
| нет аллокаций/локов в callback | инструментированный callback, счётчики | A01, A11 |
| команда применяется в заданном сэмпле | offline render + сравнение позиции | A01 |
| переполнение очереди не теряет критичные команды | сценарий с flood регуляторов | A01 |
| снимок не блокирует аудио | stress-тест публикации 60 Hz | A01, A11 |

## Как правило закреплено в коде (A01)

| Правило | Чем закреплено | Файл |
|---|---|---|
| нет аллокаций в callback | `CountingAllocator` считает аллокации внутри `RtScope`; тест требует нуля на 200 блоках | `crates/dj-audio-core/tests/rt_contract.rs` |
| нет локов, логов и I/O в ядре | статический страж: в `src` ядра запрещены `Mutex`, `RwLock`, `Condvar`, `OnceLock`, `thread::sleep/spawn`, `println!`, `std::fs` | `crates/dj-audio-core/tests/no_forbidden_primitives.rs` |
| команда применяется в своём сэмпле | блок режется на границе команды; тест проверяет тишину/звук/тишину вокруг `Play`1000 … `Stop`4000 | `crates/dj-audio-core/src/engine.rs`, `apps/dj-headless/tests/cli.rs` |
| flood регуляторов не вытесняет критичные команды | 1000 подряд идущих `SetChannelGain` схлопываются в один слот, `Play` остаётся в очереди | `crates/dj-audio-core/src/queue.rs` |
| критические команды не теряются молча | при заполнении критической полосы приходит `Ack::Rejected(QueueFull)`, счётчик растёт | `crates/dj-audio-core/src/queue.rs` |
| снимок не блокирует аудио | `Engine::snapshot()` вне RT-пути; в ядре нет разделяемого состояния, снимок — `&self` | `crates/dj-audio-core/src/engine.rs` |
| детерминизм рендера | один и тот же сценарий даёт побайтово равные WAV (sha256 в свидетельствах) | `apps/dj-headless/tests/cli.rs` |

## Первые измерения времени блока

Не эталонный стенд, а офлайновый рендер на машине разработки: 48 кГц, блок 256 кадров, бюджет
периода 5333 мкс (`dj-headless sine --frames 48000 --measure`).

| Метрика | Значение | Доля периода |
|---|---|---|
| p50 обработки блока | 2,605 мкс | 0,05 % |
| p99 обработки блока | 6,269 мкс | 0,12 % |
| max обработки блока | 17,195 мкс | 0,32 % |

Это на три порядка ниже порогов DJP-NFR-003 (p99 < 60 %, max < 85 % периода). Порог проверяется
на эталонном стенде 2-часовым живым прогоном (A11), а не здесь: офлайновый рендер не знает про
xrun'ы, отбираемое ядро и hotplug.

## Статус

Правила закреплены тестами (см. таблицу выше) и зелены в CI. `DJP-NFR-001` (нет аллокаций/локов в
callback) — `passing`. `DJP-NFR-003` (время обработки под нагрузкой на эталонной машине) остаётся
`unverified`: цифры выше получены офлайн и порогами не являются. `DJP-NFR-002` (latency) и
`DJP-NFR-004` (2-часовой soak) — A11.

## Публикация состояния (A06, исправлено)

Первая версия движка собирала снапшот прямо в рендер-потоке: брала `Mutex` на общем состоянии и
отправляла в неограниченный канал подписчикам. Для null-sink это безвредно, для живого аудиопути —
прямое нарушение контракта: мьютекс может держать поток-читатель, а канал аллоцирует.

Теперь рендер-поток только пишет числа в `StateCells` (`store` на атомиках), без аллокаций и без
блокировок. Отдельный поток-публикатор раз в 50 мс читает ячейки, собирает снапшот, увеличивает
`revision` и рассылает клиентам. Правило держит тест `publishing_a_block_does_not_allocate`: 64
вызова `publish` внутри `RtScope` обязаны дать ноль аллокаций.

Что формально остаётся в рендер-потоке: применение команд (`apply`). Сейчас это безопасно — команды
правят числа и просят переиск без ожидания, — но `Load` (декодирование и подготовка трека) обязан
уйти в управляющий поток до того, как появится.
