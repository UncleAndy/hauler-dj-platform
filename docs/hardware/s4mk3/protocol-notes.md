# S4 MK3 — заметки о протоколе (только факты)

Артефакт прохода **чтения** в clean-room-процедуре (ADR-0006, п. 9). Здесь нет кода: только факты о
протоколе с указанием происхождения. Драйвер пишется по этому документу и **не** обращается к
GPL-источникам.

Легенда происхождения:

- `observed` — снято с устройства нашими средствами, воспроизводимо;
- `public-source` — взято из публичного описания/маппинга как указатель; требует проверки на железе;
- `assumed` — гипотеза, в код не попадает до проверки.

Столбец «Проверено» относится к устройству: `public-source` по определению пока не проверен, и в код
такая строка не попадает, пока не станет `observed`. Источник public-source — публичный маппинг Mixxx
для этой модели (запись в `cleanroom-log.md`, 2026-11-22): берутся факты, не код.

## Идентификация

| Факт | Значение | Происхождение | Проверено на устройстве |
|---|---|---|---|
| Транспорт управления | HID, не MIDI | public-source | нет |
| Vendor / Product | `0x17cc` / `0x1720` | public-source | нет |
| Коллекция управления | vendor-defined, `usage_page 0xff01`, `usage 0x0`, `interface 3` | public-source | нет |
| Интерфейс дисплеев | bulk, `interface 4`, endpoint OUT `0x03` (IN отсутствует) | public-source | нет |
| Аудио | 4 playback (FL FR FC LFE), 8 capture, 44,1 / 48 / 88,2 / 96 кГц, S32_LE 24 бит | observed (A05) | да |
| Шины на аналоговых выходах | 0–1 master, 2–3 cue | observed (тон + прослушивание) | да |
| Master / Booth / Headphone volume, Headphone mix | регулируются самим аудиоинтерфейсом, в HID не приходят | public-source | нет |
| Доступ к bulk на Linux | узел `/dev/bus/usb/BBB/DDD`, нужен `udev`-правило с `MODE` | assumed | нет |
| Доступ к bulk на Windows | нужен WinUSB-драйвер для интерфейса 4 (например через Zadig) | public-source | нет |

Последние две строки — важное следствие для нашего порта: на Linux `hidraw` закрывает управление, но
не дисплеи; на Windows дисплеи требуют замены драйвера на WinUSB, что делается пользователем, а не нами.

## Входные репорты

Первый байт репорта — его номер; дальше идут байты состояния. Органы разложены по трём репортам, причём
**единого смещения между деками нет**: каждому органу смещение и бит задаются отдельно. Арифметику
«левый дек + N» применять нельзя — это не наша догадка, это наблюдение авторов маппинга.

| Репорт | Что несёт | Происхождение | Проверено |
|---|---|---|---|
| `1` | кнопки, энкодеры, часть фейдеров и ручек | public-source | нет |
| `2` | остальные кнопки, энкодеры, фейдеры и ручки | public-source | нет |
| `3` | джоги высокого разрешения: два 32-битных счётчика положения и 32-битный счётчик времени | public-source | нет |

Про репорт `3` (все факты public-source, требуют проверки):

| Смещение (от начала репорта, включая байт номера) | Смысл |
|---|---|
| `8` | счётчик времени, uint32 LE, свободно переполняется (период `2^32 − 1`) |
| `12` | абсолютное положение левого джога, uint32 LE |
| `36` | тот же счётчик времени, что и в `8` (дубль) |
| `40` | абсолютное положение правого джога, uint32 LE |

Отсюда алгоритм скорости: разность положений делится на разность счётчика времени с поправкой на
переполнение; при первом репорте предыдущего значения нет и скорость считать не из чего. Абсолютное
положение джога и относительное (сдвиг за репорт) имеют одинаковое разрешение, но разное направление
отсчёта.

Касание джога — отдельный орган (кнопка), по нему переключается режим «винил/не винил»; ёмкостный
сенсор как таковой в протоколе не отличается от обычной кнопки.

## Темпофейдер

| Факт | Значение | Происхождение |
|---|---|---|
| Диапазон по ходу | `0 … 4096` | public-source |
| Разрешение механики | `4096 / 77` ≈ 53,19 тика на мм хода | public-source |
| Различимых шагов | около 510 (шаг 8–9 тиков) | public-source |
| Центр у дек | не совпадает: левый и правый имеют собственные смещения центра | public-source |

Практический вывод: «ноль» темпофейдера — не середина диапазона, а калиброванная точка на каждой деке;
её надо измерять на устройстве и хранить в профиле, иначе темп будет уезжать при неизменном фейдере.

## Выходные репорты

| Репорт | Длина | Назначение | Происхождение |
|---|---|---|---|
| `128` | 94 байта | состояние LED: по одному байту на орган | public-source |
| `48` | 26 байт | инициализация LED джога: байт 1 = 1, байт 2 = 3, затем байт 0 = 1; шлётся дважды | public-source |
| `49` | 10 байт | моторы: две посылки по 5 байт, левая с 0, правая с 5 | public-source |
| `128`, `48`, `49` | — | порядок групп LED повторяет порядок органов, но не совпадает с ним арифметически | public-source |

Кодировка LED: значение байта — индекс цвета шагом 4 (`0` выключено, далее 18 именованных цветов до
`68`). Младшие два бита, по всей видимости, яркость `0…3`. Отметка `assumed`: в маппинге пишутся только
готовые константы цвета, яркость не проверялась.

## Дисплеи

Транспорт — bulk на интерфейсе 4, endpoint OUT `0x03`. Один кадр — это прямоугольник, а не обязательно
весь экран, поэтому обновление части экрана дешевле полного.

| Поле | Байты | Значение |
|---|---|---|
| магия | 0 | `0x84` |
| — | 1 | `0x00` |
| экран | 2 | `0` или `1` — левый или правый |
| команда | 3 | `0x21` |
| — | 4–7 | нули |
| `x` | 8–9 | big-endian |
| `y` | 10–11 | big-endian |
| `ширина` | 12–13 | big-endian, полный экран `0x0140` = 320 |
| `высота` | 14–15 | big-endian, полный экран `0x00f0` = 240 |
| пиксели | 16 … | RGB565, **старший байт первым** |
| подвал | после пикселей | `0x40, 0x00, номер экрана, 0x00` |

Полный кадр одного экрана: `16 + 320 × 240 × 2 + 4` = **153 620 байт**. При 30 кадрах в секунду это
около 4,6 МБ/с на экран — поток, который нельзя пускать через тот же путь, что и мелкие LED-пакеты, и
нельзя делать в аудиопотоке.

Происхождение всей таблицы — public-source (публичная утилита проверки экрана из того же источника).
Разрешение 320×240 и RGB565 подтверждаются ею же; на устройстве не снимали.

## Что известно о возможностях

| Возможность | Статус | Комментарий |
|---|---|---|
| Два дисплея | есть | 320×240, RGB565, по кадру на экран (public-source) |
| Моторизованный джог | есть | сила и натяжение задаются; только после ADR о безопасности |
| LED / RGB-подсветка | есть | 94 байта на выход, индекс цвета шагом 4 |
| Сенсор джога (touch) | есть | приходит как обычная кнопка |
| Четыре деки, два блока эффектов, пады, энкодеры | есть | раскладка — карта органов, см. `hardware-profile.md` |

## Как снимаем

1. Наш пробник (A09) открывает `/dev/hidraw*` для нужной коллекции и пишет сырые репорты в файл-фикстуру.
2. Одно действие — один прогон, с отметкой «что нажали»; фикстура коммитится в `tests/fixtures/`.
3. Каждая строка таблицы органов получает `observed` только после того, как байт воспроизведён дважды.
4. Исходящие пакеты на этом этапе не отправляются вообще (read-only). Это же касается репортов `48`,
   `49` и `128`: их структура записана, но отправлять их в A09 мы не будем — инициализация LED джога и
   моторы меняют состояние устройства.
5. Дисплеи — отдельный шаг и отдельный риск: на Windows нужен WinUSB, на Linux — правило `udev` на
   узел `/dev/bus/usb`. Пока не решено, что мы вообще показываем на экранах, кадры не отправляются.

Сторонние утилиты захвата допустимы как отдельные программы, но в сборку не входят и в дерево не
копируются.
