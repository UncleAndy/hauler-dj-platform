# Windows: сборка и запуск

Хост сборки — Linux (NixOS). Windows-версия собирается здесь же: движок — Rust под mingw, оболочка — Qt 6
под mingw. Linux-сборка при этом не меняется.

## Команды

```
bash scripts/windows.sh --engine    # dist/windows/dj-engine.exe
bash scripts/windows.sh --ui        # dist/windows/dj-ui.exe (Qt скачивается один раз в .cache/qt-windows)
bash scripts/windows.sh --dist      # рядом с exe: Qt, плагины, mingw-runtime, qt.conf, hauler-dj.bat, zip
bash scripts/windows.sh --msi       # установочный пакет hauler-dj-<версия>-x64.msi
bash scripts/windows.sh --all       # всё подряд
```

Переменные: `HAULER_QT_VERSION` (по умолчанию 6.8.1), `HAULER_QT_ROOT` (кэш Qt), `HAULER_ORT_DLL` (путь к
`onnxruntime.dll`, если он нужен — без него движок считает темп встроенным детектором).

## Что внутри дистрибутива

`dj-engine.exe`, `dj-ui.exe`, библиотеки Qt и mingw-runtime, `platforms/`, `styles/`, `imageformats/`,
`qml/`, `qt.conf`, `hauler-dj.bat` (поднимает движок, затем оболочку), `README.txt`.

## Отличия от Linux-версии

- **Канал.** На Linux — сокет `$XDG_RUNTIME_DIR/hauler-dj-engine.sock` (иначе `/tmp/hauler-dj-engine.sock`).
  На Windows — именованная труба `\\.\pipe\hauler-dj-engine-<пользователь>`; оболочка передаёт
  `QLocalSocket` только имя, префикс добавляет движок.
- **Каталоги.** Настройки и зеркало метаданных — `%APPDATA%\hauler-dj`; кэши (форма волны, PCM) —
  `%LOCALAPPDATA%\hauler-dj`. Правила одинаковые в коде: `crates/dj-paths`.
- **Звук.** Linux — PipeWire (cpal с фичей `pipewire`); Windows — WASAPI по умолчанию у cpal.
- **Приоритет аудиопотока (MMCSS)** пока не выставлен: первая версия играет, но под нагрузкой возможны
  щелчки. Это отдельная работа, не часть порта.
- **Установщика нет:** дистрибутив — zip с папкой.

## Границы

Проверок под Windows нет: приёмка — сборка exe и запуск `--help`. Единственный гейт проекта — существующий
`scripts/check.sh` на Linux; он должен оставаться зелёным, потому что Linux-путь порт не меняет.

## Состояние сборки (2026-11-18)

Собирается всё:

```
bash scripts/windows.sh --all          # движок, оболочка, дистрибутив, установочный пакет
bash scripts/windows.sh --msi          # только пакет, если дистрибутив уже собран
```

- `dist/windows/dj-engine.exe` — PE32+, x86-64, около 21 МБ, консольный;
- `dist/windows/dj-ui.exe` — PE32+, x86-64, около 5 МБ, консольный (`WIN32_EXECUTABLE OFF` не менялся);
- `dist/windows/hauler-dj-windows.zip` — 124 МБ: оба exe, Qt-библиотеки, плагины (`platforms` с `qwindows.dll`),
  дерево `qml`, рантайм mingw (`libstdc++-6.dll`, `libgcc_s_seh-1.dll`, `libatomic-1.dll`), `qt.conf`,
  `hauler-dj.bat`, `README.txt`;
- `dist/windows/hauler-dj-0.1.0-x64.msi` — 37 МБ, установочный пакет, см. ниже.

Linux собирается тем же деревом, что и раньше: `cargo build --workspace` и `scripts/ui.sh --build-only` проходят,
`CXXFLAGS` в dev shell не задан, поэтому C++-сборка крейтов идёт прежними флагами.

### Установочный пакет (msi)

Пакет собирается на Linux: `wixl` из msitools читает WiX-описание и пишет msi. Описание генерирует
`scripts/windows-msi.py` из готового дистрибутива — файлов больше полутора тысяч, руками такой список не ведут.

Что делает пакет:

- ставит всё содержимое `dist/windows` в `Program Files\Hauler DJ` (per-machine, нужны права администратора);
- кладёт ярлык «Hauler DJ» в меню «Пуск» на `hauler-dj.bat` — он поднимает движок, затем оболочку;
- появляется в «Программы и компоненты» с версией из `Cargo.toml`, удаляется оттуда же вместе с каталогом и
  ярлыком;
- новая версия ставится поверх старой: `UpgradeCode` постоянен, `RemoveExistingProducts` идёт после проверки
  установки, поэтому рядом не оказывается двух копий.

Идентификаторы компонентов и каталогов — UUIDv5 от пути внутри дистрибутива, поэтому одна и та же версия даёт
один и тот же пакет, а разные версии — разные `ProductCode` при общем `UpgradeCode`.

Проверка после сборки (её делает сам `--msi`): число строк в таблице `File` равно числу файлов дистрибутива
(сам zip и сам msi не упаковываются), шаблон пакета `x64;1033`. Содержимое сверялось распаковкой
(`msiextract`) и сравнением sha256 — `dj-ui.exe`, `dj-engine.exe`, `qt.conf`, `hauler-dj.bat` и файлы дерева
`qml` совпадают с дистрибутивом байт в байт.

Чего в пакете нет: `onnxruntime.dll` (Windows-сборка ORT не скачивалась, движок работает на встроенном
детекторе темпа) и ярлыка на рабочем столе — по умолчанию только меню «Пуск».

msitools в nixpkgs собирается с `doCheck = false`: его собственный набор тестов падает в песочнице на
`msibuild`, а `wixl` при этом рабочий. Путь к собранному msitools кэшируется в `.cache/msitools-path`.

### Библиотеки в дистрибутиве: два разных рантайма

Первый запуск на Windows показал «система не обнаружила libmcfgthread-2.dll» (наш `dj-engine.exe` и `dj-ui.exe`) и
«не обнаружила libwinpthread-1.dll» (Qt). Причина в том, что в пакете встречаются два разных набора C++-рантайма:

- **наш код** собран mingw из nixpkgs, а он использует mcF-потоки: `libstdc++-6.dll` из nix тянет
  `libmcfgthread-2.dll`, и этот файл лежит в замыкании компилятора в `bin/`, а не в `lib/`;
- **Qt** собран mingw с winpthreads: `Qt6Core.dll` и остальные модули требуют `libwinpthread-1.dll`, которого в
  nixpkgs нет. Файл берётся из официального инструмента Qt (`aqt install-tool ... tools_mingw1310`) — той же
  сборки, под которую собран Qt.

Плюс qml-плагины требуют куда больше модулей Qt, чем перечислишь руками (диалоги, эффекты, частицы, формы,
векторные картинки, QtTest). Поэтому `--dist` работает так: копирует базу, затем в цикле спрашивает проверку
зависимостей, чего не хватает, и докладывает эти модули из `bin` Qt — пока пропажи не кончатся.

Проверка — `scripts/windows-deps-check.py`: читает таблицы импорта каждого exe и dll (`objdump` из mingw), идёт по
зависимостям транзитивно и требует, чтобы каждая несистемная библиотека лежала в дистрибутиве. Список системных
DLL Windows — в самом скрипте. Сейчас: 2 exe, 119 библиотек, зависимостей вне дистрибутива нет.

Что это значит для запуска: в одном процессе живут две реализации потоков — mcfgthread (наш код) и winpthreads
(Qt). Каждая работает со своими объектами, и на уровне приложения они не пересекаются, но это первое, что стоит
проверить, если на Windows появятся зависания в потоках.

### Где смотреть, что происходит: два журнала

Оба процесса пишут в файлы — их видно, даже когда консоль закрыта или её нет.

```
%APPDATA%\hauler-dj\logs\dj-engine.log
%APPDATA%\hauler-dj\logs\dj-ui.log
```

На Linux то же самое в `$XDG_DATA_HOME/hauler-dj/logs/` (или `~/.local/share/hauler-dj/logs/`).

Что там видно:

- **движок**: `engine 0.1.0 listening on hauler-dj-engine-<пользователь>`, `client #N connected`, `client #N:
  handshake done`, каждая команда диджея (`command #12: Load`), и по каждой странице коллекции — `page question 12
  over ["C:\\…\\collection"]: 40 rows of 40`. Если строк нет — рядом печатается, **что спросили** (`asked [...]`)
  и **что лежит в индексе** (`stored [...]`);
- **оболочка**: `shell 0.1.0: asking for the engine on <адрес> (log <путь>)`, каждая попытка подключения и её
  ошибка, `engine answered: protocol … state … epoch …`, каждый вопрос (`question 12: offset 0, limit 200, roots
  [...]`), `load into A: <путь> (connected: yes|no)`, отказы команд.

На экране то же состояние видно в верхней панели: при отсутствии движка там написано `no engine on <адрес>` —
именно тот адрес, по которому стучались.

Первое, что стоит сравнить, когда список пуст: адрес в баннере оболочки и в баннере движка (они обязаны
совпадать), а затем `asked [...]` и `stored [...]` в журнале движка.

### Подробная диагностика

Подробность задаётся `HAULER_LOG` — `error`, `warn`, `info` (по умолчанию), `debug`, `trace`. Запускатор в
дистрибутиве ставит `trace`, пока идёт отладка на реальных машинах.

Файлы (каждый поворачивается на 8 МБ, одна предыдущая копия остаётся):

```
%APPDATA%\hauler-dj\logs\dj-ui.log               оболочка
%APPDATA%\hauler-dj\logs\dj-engine.log           движок
%APPDATA%\hauler-dj\logs\dj-engine-console.log   консоль движка целиком, на случай падения до открытия журнала
```

Что пишется на `trace`:

- **окружение при старте** (оба процесса): версия, путь к exe и время файла, ОС и архитектура, pid, каталог
  запуска, все аргументы, переменные `APPDATA`/`LOCALAPPDATA`/`USERPROFILE`/`XDG_*`/`ORT_DYLIB_PATH`/`HAULER_LOG`,
  каталоги данных, настроек и кэша, адрес канала и путь к журналу — то есть чем одна установка отличается от
  другой;
- **звук**: перечень устройств вывода с номерами, чем именно открыт поток (имя, каналы, частота, размер блока),
  причина отказа устройства и переход на null sink;
- **состояние раз в секунду**: `state: rev …, ticks …, snapshots …, clients …, decks [A=Ready <путь>, …]` — видно,
  движется ли публикация и что дека считает про свой трек;
- **сообщения клиента раз в секунду**: `client in 1 s: Seek x47, Play x1` — рука на пластинке не забивает журнал;
- **команды** (`debug`) с номером и названием, **подтверждения** и **отказы** с причиной;
- **страница коллекции**: вопрос (id, смещение, лимит, корни, поиск), ответ (строки/всего, режим, корни, фильтр) и
  причина, по которой ответ не принят: `answer N dropped: asked X, already had Y, mode Z`;
- **деки в оболочке**: смена состояния (`Loading` → `Ready`/`Failed`), путь и пики;
- **сообщения Qt** (предупреждения QML, плагины) — в тот же файл.

Переписка двух журналов читается по времени: строка оболочки `question 2 …` и строка движка `page question 2 over
[…]` относятся к одному вопросу по номеру.

### Первый запуск на Windows: что нашлось и что исправлено

Владелец принёс четыре снимка с рабочей машины. Три оказались одной болезнью, четвёртая — отдельной.

1. **Оболочка подключалась к движку один раз.** Запускатор поднимает оба процесса сразу, и если движок не успел
   открыть трубу, окно оставалось живым, но глухим: пустая коллекция, пустой список жанров, дека молча
   отказывается грузить — и ни строки в терминале. Теперь `BridgeClient` повторяет попытки (первые 10 секунд по
   250 мс, дальше по 2 с), пишет каждую в терминал и прекращает при выходе. Свидетель:
   `--reconnect-check` — клиент стартует раньше «движка» и обязан к нему вернуться.
2. **Корни коллекции сравнивались через `/`.** Строка индекса отбирается по `path LIKE '<корень>/%'`, а на
   Windows и корень, и путь пишутся с `\`: список не находил ни одной строки. Теперь корень даёт два префикса,
   с `/` и с `\` — это работает и на смешанных данных. Свидетель:
   `a_page_finds_rows_under_a_windows_root`.
3. **Импорт мог писать в рабочий каталог.** Каталог импорта брался как есть: пустой корень — и копии ложились
   рядом с движком, а индекс хранил относительные пути, которых список (он спрашивает про абсолютные каталоги) не
   видит. Теперь оболочка никогда не отдаёт пустой корень (`roomiestRoot` берёт первый корень или каталог
   коллекции движка), а движок пустой или относительный корень приводит к своему каталогу коллекции и говорит об
   этом в терминал. Свидетели: `an_import_without_a_folder_lands_in_the_collection`,
   `a_relative_import_folder_is_made_absolute`.
4. **Кнопка «Genre filter…» молчала, когда жанров нет.** Она была погашена — для обеих версий. Теперь она
   открывает объяснение: жанров ещё нет (их даёт тег или анализ) либо движок не отвечает. Свидетель — сама
   проверка на снимке, кода не потребовалось.

Проверено под wine на настоящих exe: импорт ложится в указанный корень, «the walk lists 1 rows, the index page 1,
0 differ», жанры приходят из таблицы, фильтр по жанру оставляет строку, загрузка из списка отвечает
`loaded Z:\tmp\wincoll3\A\L\Alpha - Page.wav into A` за 286 мс; оболочка, запущенная раньше движка,
подключается сама.

### Что пришлось решить в окружении хоста

1. **Сборочные скрипты — программы хоста.** rustc линкует их своим lld через папку `gcc-ld` внутри тулчейна; в
   nix-шелле она пуста. Скрипт кладёт туда ссылку на `ld.lld` из nix — ничего вне тулчейна не трогается.
2. **C++-крейты читали только `CXX`.** Для кросс-сборки cargo даёт `CXX_x86_64_pc_windows_gnu`, а `CXX` — это
   хост. Теперь оба `build.rs` сначала смотрят переменную цели; иначе в библиотеку для Windows попадали
   хостовые объекты, и линкер говорил только «символы не найдены».
3. **`libpthread.a` в mingw из nixpkgs нет** (потоки собственные). chromaprint просит это имя — пустой архив в
   кэше сборки удовлетворяет линкер.
4. **mingw в nix собран с mcF-потоками.** Часть `libstdc++` (`gthr.h`) живёт в `mcfgthread`, а заголовки и
   библиотека — в отдельных выходах замыкания компилятора. Скрипт находит их через `nix-store -qR` и передаёт
   в `CXXFLAGS_<target>` и `RUSTFLAGS`. Тот же путь нужен CMake (`-DCMAKE_CXX_FLAGS`, `-DCMAKE_EXE_LINKER_FLAGS`),
   иначе не проходит даже пробная компиляция: mingw добавляет `-lmcfgthread`.
5. **Инструменты Qt для хоста.** Официальная Linux-сборка Qt — обычные бинарники под FHS: они ждут
   `/lib64/ld-linux-x86-64.so.2`, которого на NixOS нет. `scripts/windows.sh` собирает FHS-окружение
   (`buildFHSEnv` с нужными библиотеками) и заменяет каждый инструмент в `bin/` и `libexec/` обёрткой, которая
   запускает настоящий файл внутри этого окружения. Windows-копии инструментов не запускаются на хосте вообще,
   поэтому Qt обязан брать хостовые.
6. **`QT_HOST_PATH` сам по себе не переключает инструменты.** Нужен ещё `QT_HOST_PATH_CMAKE_DIR` — иначе Qt
   берёт `qmlimportscanner.exe` из Windows-набора и падает с «permission denied».
7. **Рантайм mingw.** Qt из aqt собран другим mingw и своих `libstdc++-6.dll` не приносит; `--dist` берёт их из
   того же тулчейна, которым собран exe.

### Чего в песочнице проверить нельзя

Запуск на настоящей Windows: два процесса, именованная труба, WASAPI, чтение `%APPDATA%`. В дистрибутиве нет
`onnxruntime.dll` (Windows-сборка ORT не скачивалась) — движок работает на встроенном детекторе темпа.
