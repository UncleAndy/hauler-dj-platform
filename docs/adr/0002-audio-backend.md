# ADR-0002: основной аудиобэкенд

- **Статус:** proposed — сам backend не выбран
- **Решение владельца (2026-11-04):** backend не выбирать умозрительно; сначала измерения A05
- **Требования:** DJP-NFR-002…006, DJP-ARCH-007, DJP-ARCH-008
- **Блокирует:** выбор реализации `dj-audio-io` (R0-код), но **не** R0-демо: интерфейс адаптера общий

## Вопрос

Чем выводить звук и управлять маршрутизацией: CPAL как переносимый адаптер или прямой
PipeWire/JACK-backend с полным контролем портов и quantum?

## Варианты и что они означают на практике

### A. Только CPAL

- **Даёт:** один путь сборки, переносимый API (Linux/Windows/macOS), MIT, уже компилируется в нашем
  shell (`cpal 0.16` + alsa-sys проверены в A00), минимальный объём кода.
- **Не даёт:** тонкого контроля над выбором портов и маршрутизацией master / headphones / booth,
  прямого управления quantum/period и приоритетами PipeWire-графа. На Linux CPAL идёт через ALSA
  (или JACK при включённой фиче), то есть между движком и устройством стоит ещё один слой.
- **Риск:** раздельные выходы S4 MK3 (master/cue/booth) могут оказаться недоступны как отдельные
  каналы — а это DJP-MIX-003 и R1.

### B. Прямой PipeWire (или JACK)

- **Даёт:** адресация узлов и портов, явные маршруты, контроль `quantum`/задержки, hotplug,
  сосуществование с сессией рабочего стола; это ровно то, что требует DJP-ARCH-007/008.
- **Не даёт:** переносимости (Linux-only — для R0 это не ограничение, DJP-ENV-001), плюс больше
  кода и зависимость от версии PipeWire (у нас 1.6.6).
- **Риск:** собственный цикл ожидания/таймингов нужно написать корректно, иначе xrun-ы.

### C. Гибрид: CPAL сейчас, PipeWire-адаптер при необходимости

- **Даёт:** быстрый старт R0 и возможность закрыть многоканальную маршрутизацию позже, не меняя
  `dj-audio-io` (у него уже интерфейс адаптера, а не конкретный backend).
- **Стоит:** два поддерживаемых пути, два набора тестов.

## Критерии решения (заданы до измерений)

1. Видны и адресуемы нужные каналы устройства (S4 MK3: master, cue, booth) без ручных обходов.
2. 48 кГц / 256 frames, 2 и 4 деки, ≥2 ч: `app_xruns = 0`, p99 < 60 % периода (DJP-NFR-003/004).
3. Возможность 128 frames в перспективе (DJP-NFR-005) и измеренная round-trip latency (DJP-NFR-006).
4. Hotplug и сосуществование с PipeWire-сессией рабочего стола.
5. Стоимость поддержки: один путь против двух.

## Решение: сначала измерения (2026-11-04)

Владелец подтвердил: выбор делается по данным, а не по предпочтению. Ниже — что именно измеряет A05
и по каким порогам принимается решение.

Делать **A05 как измерение, а не как выбор**: R0 собирать на CPAL (вариант C, первая половина),
и в том же спайке отдельно перечислить PipeWire-порты и проверить, видит ли CPAL раздельные выходы
S4. Если видит и держит пороги по п.2 — остаёмся на CPAL: один путь дешевле. Если нет — добавляем
PipeWire-backend, а CPAL остаётся для портативности/тестов. Так ADR-002 не тормозит R0 и решается
фактами, которые всё равно нужны A10.

## Шаг 0 — пробник устройств (без движка)

Вопрос «видит ли CPAL каналы S4 MK3» решается до появления RT-ядра: read-only перечисление устройств
плюс короткий прогон на дефолтном выходе. Инструмент уже в репозитории: `apps/dj-audio-probe` (A05).

```bash
# на рабочем столе, S4 MK3 подключён, другие аудиоприложения закрыты
cargo run -p dj-audio-probe -- --list-only          # сначала без звука
cargo run -p dj-audio-probe -- --json --silent --out /tmp/s4-probe.json
```

Что решает дело: `output_devices`, `devices_with_more_than_2_channels`, список `channels` у каждого
устройства, `buffer_frames` и блок `trial` (`callbacks`, `p99_ms`, `max_ms`, `gaps_over_1_5x_period`).
Пробник не открывает входные потоки, на устройство идёт тишина или тихий тон 440 Гц, контроллеру
ничего не отправляется — прошивка и HID не затрагиваются.

Результат (`/tmp/s4-probe.json`) кладётся в `docs/qa/evidence/A05/` как отправная точка этого ADR.
Exit code 3 означает «устройств не видно», то есть замер не состоялся, — это не вердикт о CPAL.

## Протокол измерений A05 (что должно быть получено)

Измерения выполняются на эталонном стенде (`docs/qa/reference-rig.md`) владельцем: в песочнице агента
нет `/dev/snd`. Минимум для решения:

| # | Измерение | Как | Порог/критерий |
|---|---|---|---|
| 1 | какие устройства и каналы видит CPAL | `cpal` enumeration + `pw-cli ls Port` / `pw-link -l` | нужны раздельные master / cue / booth у S4 MK3 |
| 2 | 48 кГц / 256 frames, 2 деки, 2 ч | прогон движка, счётчики `app_xruns`, `callback p99/max` | xrun приложения = 0, p99 < 60 % периода |
| 3 | 128 frames (низкая задержка) | тот же прогон с меньшим блоком | попытка; вердикт `works` / `not on this host` |
| 4 | round-trip latency | loopback-кабель, импульс | измерить фактически, без обещаний |
| 5 | hotplug/reconnect | отключить и вернуть устройство | звук не падает, устройство возвращается |

Результат — `docs/qa/evidence/A05/benchmark.json` + `summary.md`; после этого ADR-002 переводится в
`accepted` с указанием, какой вариант выбран и на каких числах.

## Что уже известно

- PipeWire 1.6.6 и ALSA 1.2.14 доступны; `cpal` собирается и линкуется в нашем shell.
- Физические измерения не проводились: в песочнице агента нет `/dev/snd` (`cpal` видит 0 устройств),
  поэтому пункты 1–3 остаются `not tested` до прогона на стенде владельца.
