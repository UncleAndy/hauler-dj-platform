# ADR-0003: мост QML ↔ Rust

- **Статус:** proposed
- **Требования:** DJP-ARCH-001, DJP-ARCH-004, DJP-NFR-007, DJP-NFR-016, DJP-UI-001
- **Блокирует:** стабилизацию A06 (не мешает R0-каркасу, где UI ещё не связан с движком)

## Вопрос

Один процесс (Qt-объект/C ABI поверх Rust, снимки и команды в памяти) или отдельный UI-процесс,
который общается с движком версионированными сообщениями?

## Варианты и что они означают на практике

### A. Один процесс, in-process мост (C ABI или CXX)

- **Даёт:** минимум задержки и кода, простая сборка (одна линковка), удобная отладка.
- **Не даёт:** изоляции. Зависший или упавший UI в одном процессе способен утащить за собой движок:
  `QML`-рендеринг, GC-паузы, плагины Qt — всё в общем адресном пространстве. Требования
  DJP-NFR-007 (уничтожение UI не останавливает буферизованный звук) и DJP-NFR-016 выполняются
  только «по договорённости» — за счёт дисциплины потоков, а не архитектуры.
- **Тестирование:** UI-тесты тащат за собой аудиодвижок; снимки состояния проверяются в живом процессе.

### B. Отдельный UI-процесс + IPC

- **Даёт:** жёсткую границу: падение/зависание/рестарт UI не касается аудиопотока (это прямой вход в
  DJP-NFR-007/016 и в acceptance A06 «UI can restart without invalidating engine»). Headless-тесты
  движка и UI-тесты идут раздельно, снимки — обычные сериализованные структуры, которые можно
  сравнивать в тестах.
- **Стоит:** сериализация снимков 30–60 Гц (килобайты, не проблема для CPU), протокол нужно
  версионировать (те же `state-v1`/`command-v1`), чуть больше кода на старте и локальный сокет/pipe.

## Критерии (те же, что в ТЗ)

1. UI не может задержать аудиопоток даже при зависании рендеринга.
2. Снимок с `revision`/`epoch` доходит без блокировок аудио; устаревший снимок ≠ подтверждение команды.
3. Перезапуск UI не ломает и не перезапускает движок.
4. Договороспособность: сколько стоит сериализация против скорости разработки и тестируемости.

## Рекомендация (архитектор; решение — за владельцем)

Для **R0** — вариант A, но с контрактом, который не придётся переделывать при переходе на B:
команды и снимки уже сейчас описываются как плоские DTO в `dj-domain`, `dj-bridge` только
преобразует их в/из представления Qt, QML не видит ни одной DSP-структуры. Тогда смена A→B — это
замена транспорта (вызов → сообщение), а не переписывание контрактов. Переход обязателен, если A06
покажет реальное влияние UI на звук или если понадобится перезапуск UI без остановки воспроизведения
на живой сессии.

## Текущее состояние

`apps/dj-ui` собирается и запускается без движка; `dj-bridge` — пустой крейт. Ни C ABI, ни IPC не
написаны: этот выбор не делается «по факту уже написанного кода».
