# ADR-0003: мост QML ↔ Rust

- **Статус:** accepted (2026-11-04, решение владельца)
- **Требования:** DJP-ARCH-001, DJP-ARCH-004, DJP-NFR-007, DJP-NFR-016, DJP-UI-001
- **Разблокирует:** A06, фиксирует формат контрактов A01

## Решение

**Отдельный UI-процесс.** Аудиодвижок — самостоятельный процесс, который владеет аудиоустройством и
не зависит от существования UI. Qt/QML-оболочка — клиент: отправляет команды и получает снимки
состояния по локальному транспорту (unix-сокет), сообщениями `command-v1` / `state-v1`.

## Почему именно так

Владелец зафиксировал приоритет: воспроизведение звука — главная функция приложения, и оно должно быть
максимально надёжным. При таком приоритете in-process мост проигрывает по единственному, но
решающему пункту: в одном адресном пространстве зависший рендер, GC-пауза, падение плагина Qt или
`SIGSEGV` в UI забирают с собой звук. Изоляция процессом делает это невозможным по конструкции, а не
по договорённости между потоками:

| Сценарий | Один процесс | Отдельный UI-процесс |
|---|---|---|
| UI завис (рендер/GC) | звук может прерваться | звук идёт |
| UI упал (`SIGSEGV`) | звук останавливается | звук идёт, UI перезапускается |
| UI перезапущен | обычно нужен рестарт движка | движок не затронут (acceptance A06) |
| Движок упал | звук останавливается | звук останавливается (неустранимо) |

Обратное направление (B → A) при необходимости дешевле, чем A → B: контракт сообщений и клиент уже
есть. Поэтому выбирается более строгий вариант.

## Последствия

1. **A01.** `Command`, `Ack`, `Snapshot` — это не просто структуры в памяти, а **формат сообщений**:
   сериализуемые, версионированные (`schemas/command-v1.json`, `state-v1.json`), с явным поведением
   при несовместимой версии. Контракт фиксируется до кода IPC.
2. **A06.** Появляется процесс-движок (бинарник `apps/dj-engine`) и клиент в `apps/dj-ui`:
   сокет с правами пользователя, реконнект, backpressure, коалесинг регуляторов (DJP-ARCH-003),
   отдельный канал для критичных команд (Stop/Load/Unplug не теряются при потоке ручек).
3. **`apps/dj-headless`** перестаёт быть отдельной реализацией: он поднимает тот же движок без UI,
   что и делает возможными offline-тесты (A01/A11).
4. **Снимки 30–60 Гц.** Сериализация небольших DTO; на R0 достаточно JSON (читаемость и отладка),
   переход на бинарный формат — отдельным решением с замером, версия схемы при этом не меняется.
5. **Отказоустойчивость явно ограничена:** падение движка останавливает звук; автоперезапуск движка
   не возобновляет воспроизведение сам, состояние восстанавливается из сессии (A08).
6. **Тестируемость:** протокол можно гонять без GUI (клиент-заглушка), UI-тесты не требуют
   аудиоустройства.

## Что заставит пересмотреть

Замеренный overhead сериализации/транспорта, влияющий на отзывчивость управления (клавиши, фейдеры)
или на CPU в эталонном прогоне. Тогда допускается in-process мост — но только отдельным ADR с
измерениями и с сохранением требования «убийство UI не останавливает звук» другим способом.

## Текущее состояние

`apps/dj-ui` собирается и запускается без движка; `dj-bridge` — пустой крейт; `apps/dj-engine`
появится в A01. Ни C ABI, ни IPC пока не написаны — реализация начинается с контрактов.
