# ADR-0010: RT-приоритет, размер блока и счётчик xrun

- **Статус:** accepted (2026-11-05)
- **Дата:** 2026-11-05
- **Контекст:** A05 (живой вывод), замеры с разделением CPU/вытеснение
- **Требования:** DJP-NFR-002, DJP-NFR-004

## Что измерено

15 минут живого вывода, петля 2 с, системное устройство, 48 кГц / 256 кадров:

| Показатель | Значение |
|---|---|
| стоимость графа (`render`) p50 / p99 / max **по CPU** | 6 / 10 / **81 мкс** |
| стоимость блока по стенному времени, худший | 2657 мкс |
| невольные переключения контекста | **3323** (3,7 в секунду) |
| суммарная задержка в очереди | **635,7 мс** |
| максимальный интервал колбэка | **14,636 мс = 2,74 периода** |
| провалов деки | 0 при 449 переходах петли |

Разделение по каждому дорогому блоку решает вопрос: у блока с `render_us` 2256 мкс **`cpu_us` = 14**,
у 1647 мкс — 14, у 1049 — 15, у 996 — 6. То есть код работал микросекунды, а всё остальное время поток
не исполнялся. **Хвост — вытеснение, не наш граф.** Настоящая стоимость блока — единицы микросекунд,
худшая замеренная — 81 мкс, это 1,5 % периода.

## В чём проблема

Интервал 14,6 мс означает, что за 2,74 периода пришёл один колбэк. Мы выдали корректное число кадров
(168 743 × 256 = 43 198 208), но буфер устройства за это время почти наверняка опустел: наш счётчик
этого не видит, потому что считает только свою сторону. По DJP-NFR-002 и DJP-NFR-004 вердикт
выносится по **xrun'ам**, а счётчика xrun'ов у нас нет.

Вторая половина проблемы: поток колбэка живёт в `SCHED_OTHER`. На обычном десктопе это 3,7
вытеснения в секунду; на загруженной машине — больше. Никакая оптимизация графа этого не лечит.

## Варианты

| Вариант | Суть | Цена | Кому годится |
|---|---|---|---|
| **A. RT-приоритет из приложения** | попросить `SCHED_FIFO` (Linux: rtkit через D-Bus или `CAP_SYS_NICE`; Windows: MMCSS «Pro Audio»; macOS: thread time-constraint) | требует прав или брокера; ошибку надо обрабатывать, а не падать | всем, но не гарантируется на чужой машине |
| **B. RT-приоритет из упаковки** | systemd-юнит пользователя с `CPUSchedulingPolicy=fifo`, `CPUSchedulingPriority=20…50`; на NixOS — модуль в flake | привязка к способу установки | Linux/NixOS — основная платформа |
| **C. Больший блок** | 512 кадров = 10,7 мс периода: вдвое больше слака | вдвое больше задержка вывода; для DJ это уже на грани | как настройка, не как дефолт |
| **D. Диагностика вместо лечения** | измерить политику и приоритет потока, показывать предупреждение, когда поток не RT и опаздывания растут | не улучшает звук само по себе | обязательно в любом случае |

## Решение (предлагается)

1. **D — всегда:** отчёт содержит `thread_scheduling` (`policy`, `rt_priority`, `nice`); в UI —
   предупреждение, если `policy != fifo` и `late_callbacks > 0`.
2. **B — основной путь для Linux/NixOS:** юнит с RT-политикой в упаковке; приложение не требует
   привилегий и не пытается их получить.
3. **A — как попытка с честным отказом:** при старте пробуем поднять приоритет; если прав нет,
   пишем в отчёт `rt_denied` с причиной, не выдавая это за успех.
4. **C — настройка** `audio.block_frames` (256 по умолчанию, 512 как «устойчивый» профиль),
   потому что это ровно тот компромисс, который пользователь должен выбирать сам.
5. **Счётчик xrun — обязательный прибор** до любых заявлений о «нулевых xrun»: читать ошибки узла
   PipeWire (`pw-top`/`pw-dump`), а на ALSA — ошибки потока в колбэке cpal, и складывать в отчёт.

## Как проверять

- Прогон 15 минут на простаивающей машине: `thread_scheduling.policy = fifo`, `late = 0`,
  `xruns = 0`.
- Прогон под нагрузкой (сборка, видео): xrun'ы допустимы, но их **число должно быть измерено**, а не
  выведено из «вроде не слышно».
- Порог вердикта для NFR-004 — ноль xrun'ов за 2 часа на зафиксированном стенде (A11).

## Решение владельца (2026-11-05)

Согласовано: **RT-приоритет выдаётся упаковкой**, приложение лишь проверяет и предупреждает.
Пункты 1–4 приняты, вариант «просить приоритет изнутри через rtkit» отклонён.

Реализовано:

- `dj_audio_io::realtime_status` — вердикт по политике потока: `realtime: bool`, `policy`,
  `advice` с указанием, что править; тесты на fifo/other/нечитаемо, причём «нечитаемо» не считается
  успехом;
- отчёт пробника содержит `realtime { ok, policy, advice }` и `thread_scheduling`;
- при старте без RT пробник пишет предупреждение в stderr;
- спецификация упаковки — `docs/operations/realtime-audio.md` (systemd-юнит, NixOS, проверка через
  `systemd-run --user --scope -p CPUSchedulingPolicy=fifo`).

### Поправка рецепта (2026-11-05, по факту запуска)

Первая версия `docs/operations/realtime-audio.md` предлагала `systemd-run --user --scope -p
CPUSchedulingPolicy=fifo`, и владелец получил `Unknown assignment: CPUSchedulingPolicy=fifo`.
Причина: это свойство сервиса, а не scope. Проверено на systemd 260.

Из этого следует уточнение к решению: приоритет выдаёт **либо лимит `rtprio` из PAM плюс лаунчер с
`chrt -f 20`**, либо **системный юнит**. Пользовательский менеджер systemd приоритет поставить не
может: свойство принимается, но применяется с `Failed to set scheduling policy, ignoring`. Поэтому
проверка в приложении обязательна — она ловит именно этот случай, когда «настроено» не значит
«применено».

Счётчик xrun остаётся долгом: без него NFR-002 и NFR-004 не выносятся.
