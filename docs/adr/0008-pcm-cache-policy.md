# ADR-0008: политика PCM-кэша по форматам

- **Статус:** accepted (2026-11-05, решение владельца)
- **Требования:** DJP-MEDIA-001, DJP-MEDIA-002, DJP-NFR-001, DJP-ARCH-005, DJP-ENV-006
- **Разблокирует:** A02 (`dj-codec`), A11 (замеры декодирования)

## Контекст

Lossy-форматы устроены фреймово: MP3 — 1152 сэмпла на фрейм (26,1 мс при 44,1 кГц), длительность в
VBR не выводится из размера файла, а начало трека содержит задержку кодировщика (~1105 сэмплов) и
padding в конце. Всё это делает потоковое декодирование с точным seek и gapless заметно сложнее, чем
у lossless.

Владелец зафиксировал принцип: **решение принимается по свойствам файла при загрузке в деку, а не по
поведению во время воспроизведения.** Никаких «адаптивных переключений» в потоке: в сете поведение
трека не должно зависеть от того, как быстро отработал диск в конкретный момент.

## Решение

### 1. Формат файла определяет стратегию

| Класс | Форматы | Стратегия | Почему |
|---|---|---|---|
| **Lossless** | WAV, AIFF, FLAC | потоковое декодирование + индекс (смещения блоков, точный seek, gapless от кодека) | декодер дешёвый, seek по индексу точен, конвертация даёт только расход места |
| **Lossy** | **MP3 (CBR и VBR)**, Ogg Vorbis | **декодирование в PCM при загрузке**, воспроизведение из кэша | фреймовая структура, VBR-длительность, обрезка delay/padding один раз, seek в любую точку |

VBR — худший случай внутри MP3, но CBR попадает в тот же класс: иначе два трека в одном сете ведут
себя по-разному, а это в работе хуже, чем лишние мегабайты кэша.

### 2. Кэш на диске по умолчанию, но это настройка

| Параметр (конфиг) | По умолчанию | Смысл |
|---|---|---|
| `media.pcm_cache.enabled` | `true` | включён ли кэш для lossy |
| `media.pcm_cache.storage` | `disk` | `disk` или `memory` |
| `media.pcm_cache.max_size_gb` | `8` | лимит (≈150 треков по 5 мин в 16 бит) |
| `media.pcm_cache.sample_format` | `i16` | `i16` / `i24` / `f32` |
| `media.prefetch_seconds` | `2` | окно PCM перед декодером (750 КиБ/дека) |
| `media.long_file_minutes` | `15` | порог «длинного файла» |
| `media.long_file_ready_seconds` | `60` | сколько PCM нужно для `Ready` у длинного файла |

`memory` — второй вариант, который допускается настройкой: 5-минутный трек в f32 занимает 115 МБ,
4 деки — 460 МБ, 40-минутный микс — 1,8 ГБ, поэтому по умолчанию диск.

### 3. Что значит `Ready`

- lossless: индекс построен, первое окно префетча заполнено;
- lossy: PCM записан **полностью**;
- файл длиннее `media.long_file_minutes`: `Ready` после `long_file_ready_seconds` PCM, остальное
  догружается фоном, прогресс виден в состоянии деки (поле в `state-v1`, ADR-0006).

`Play`, пришедший раньше `Ready`, ставится в очередь деки (контракт A03), а не теряется.

### 4. Идентичность и обслуживание кэша

- путь: `$XDG_CACHE_HOME/hauler-dj/pcm/` — **никогда** рядом с музыкальной библиотекой;
- ключ: sha256 содержимого файла + частота + формат сэмпла + версия формата кэша (не путь: иначе
  «играет старую версию трека» после замены файла);
- LRU с жёстким лимитом `max_size_gb`; загруженные и предзагруженные деки **пинуются**;
- кэш всегда регенерируем: источник истины — только исходный файл;
- запись — только из фонового воркера, никогда из аудиопотока.

### 5. Бюджеты (пороги до данных)

| Событие | Бюджет |
|---|---|
| `Load` → `Ready`, типовой трек | ≤ **3 с** (при `long_file_minutes` действует исключение выше) |
| `Seek` за пределы окна префетча | p99 ≤ **30 мс** |
| `Seek` внутри окна | **0** обращений к декодеру и диску (проверяется счётчиком) |
| Звук при скретче | только из окна, декодер в это время не участвует |

Бюджет `Ready` выполним, если декодер даёт ≥ ~100× реального времени (5-минутный трек за 3 с). Это
первое, что измеряет A02; если Symphonia даёт 50×, загрузка честно показывает прогресс и идёт дольше,
либо PCM готовится фоновым воркером после импорта — решение принимается по измеренному числу.

## Альтернативы

- **Конвертировать всю библиотеку заранее** (10 000 треков ≈ 0,53 ТБ): отвергнуто — часы импорта,
  инвалидация, зависимость от частоты устройства (ADR-0005).
- **Потоковое декодирование для всех форматов:** отвергнуто владельцем: у MP3 точный seek и gapless
  требуют заметно больше логики в горячем пути, чем у lossless, а поведение в сете становится
  зависимым от состояния диска.
- **Адаптивное решение по замеру во время игры:** отвергнуто принципиально — триггер только свойства
  файла.

## Следствия

1. `dj-codec` содержит две стратегии (`Streaming { index }`, `DecodeToCache { policy }`) и подсистему
   кэша (запись, LRU, пиннинг, инвалидация по хэшу, GC).
2. Метрики A02: скорость декодирования (×realtime по форматам), `t_ready` холодный/горячий,
   p99 seek, счётчик обращений к декодеру при seek внутри окна, hit ratio, размер кэша.
3. `state-v1` (A03) получает прогресс подготовки деки — иначе прогресс длинного файла некуда показать,
   в том числе на экран контроллера.
4. Настройки (DJP-ENV-006) получают группу `media.*` из таблицы выше.

## Открыто

- Формат файла кэша (сырой PCM + заголовок в sidecar или WAV) — решится при реализации, наружу не
  влияет.
- Нужен ли предпрогрев кэша для «следующего» трека в плейлисте (вероятно да, отдельным пунктом A08).
