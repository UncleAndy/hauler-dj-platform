# Загрузка трека в деку (предусловие A07)

Дека умеет играть файл: `Load` в контракте, загрузчик вне аудиопути, вложение на границе блока.

## Почему это не в колбэке

Открыть файл, прочитать заголовок, собрать окно предпросмотра и (для lossy) PCM-кэш — это
миллисекунды, иногда секунды. Колбэк имеет 5,3 мс. Поэтому `Load` **не** применяется рендер-потоком:

```
клиент ──Load──► поток-загрузчик ──GraphLoad::Attach──► граф (на границе блока)
                        └────────DeckUpdate──────────► публикатор (Loading → Ready)
```

- Клиентский поток загружает команду в очередь загрузчика и сразу отвечает `Accepted` — не
  `Applied`, потому что ничего ещё не применено. Дека играбельна, когда состояние говорит `Ready`.
- Загрузчик решает про PCM-кэш **при загрузке**, по формату файла (ADR-0008), а не в середине
  воспроизведения, где это было бы провалом.
- Граф забирает готовый источник через `try_recv` (не аллоцирует) и вкладывает его в начале блока.
  Старый источник не освобождается в колбэке: он паркуется в предвыделенный вектор и живёт до
  остановки движка — `free()` большого буфера внутри блока дороже самого блока.

## Проверено

Реальный протокол, настоящий процесс движка, файл сгенерирован своим же рендерером:

```
welcome: bridge-v1
ack: {'command_id': 1, 'status': 'Accepted'}
deck A load: Ready
track: track-test | duration_frames: 144000
playing: True | frame: 2304 | levels: {'peak_left': 0.366, 'peak_right': 0.366}
```

3 с × 48 000 = 144 000 кадров — как в файле; пики 0,366 соответствуют амплитуде 0,5 в файле после
микшера и лимитера, то есть звук идёт из файла, а не из встроенного тона.

Оболочка проверяется тем же гейтом (`scripts/ui.sh --engine-check`): UI сам просит `Load`, ждёт
`Ready`, затем `Play`, `Cue Set`, `Cue Jump`:

```
dj-ui: sent Load(A) as command 1
dj-ui: deck A is ready: track
dj-ui: sent Play(A) as command 2
dj-ui: sent Cue(Set 0) as command 3
dj-ui: sent Cue(Jump 0) as command 4
dj-ui: self-check passed: Play and Cue acknowledged and visible in the snapshot (sample 14592, rev 6) after 231 ms
```

## Тесты

| Тест | Что держит |
|---|---|
| `a_load_is_routed_away_from_the_audio_callback` | `route()` отправляет `Load` загрузчику, а транспорт — рендеру |
| `a_stray_load_reaching_the_render_loop_is_refused_rather_than_pretended` | если маршрут сломан, `apply` отвергает `Load`, а не врёт `Applied` |
| `a_prepared_track_is_attached_at_a_block_boundary_and_plays` | настоящий WAV: разбор, `Ready`, вложение внутри блока, звук на master |
| `an_eject_clears_the_deck_inside_the_block` | `Eject` возвращает деку в `Empty` |
| `the_callback_path_does_not_allocate` | 16 блоков с командами и вложениями — 0 аллокаций |

## Ограничения

- Ресемплинга нет: файл должен быть в частоте графа (48 кГц); 44,1-кГц файл сейчас играл бы с
  неверной высотой. Это A04/M2 (`SetTempoRatio` по той же причине отвергается).
- Прогресс загрузки публикуется как `Loading { progress: 0.0 }` и не обновляется: загрузчик сообщает
  начало и конец, у `Prefetcher` нет обратного отсчёта. Для длинных файлов это A08.

## Почему свой браузер файлов, а не FileDialog

Первая версия использовала `QtQuick.Dialogs.FileDialog`. На Linux это нативный диалог GTK/портала, и в
окружении без `gsettings-desktop-schemas` он **валит весь процесс**:

```
GLib-GIO-ERROR: Settings schema 'org.gtk.Settings.FileChooser' is not installed
```

Оболочка не имеет права падать из-за отсутствующего пакета рабочего стола: пользователь в этот момент
теряет и UI, и связь с движком. Вторая попытка — `Qt.labs.folderlistmodel` — упирается в то, что модуль
не собран в этой сборке Qt. Поэтому листинг каталога делает `FileBrowser` на `QDir`: ни GTK, ни
портала, ни QML-расширений, только QtCore и QtQuick.

Проверка вошла в гейт: `dj-ui --dialog-check` открывает браузер над домашним каталогом и падает, если
листинг не собрался. Ранее такой дефект обнаруживался только кликом пользователя — то есть после
поставки.
