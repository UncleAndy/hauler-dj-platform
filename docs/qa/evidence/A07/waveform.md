# Волновые формы: конверт и кэш (A07, часть 1)

`crates/dj-analysis` больше не заглушка: конверт (min/max на столбец), кэш на диске с отпечатком
файла, ссылка на конверт в состоянии деки.

## Время — в кадрах источника

Столбец `n` покрывает кадры `[n * frames_per_bucket, (n + 1) * frames_per_bucket)`. Поэтому
плейхед ставится по `frame / frames_per_bucket` без масштабных поправок — это и есть требование
DJP-MEDIA-003. Тест `the_timebase_maps_a_playhead_to_the_right_column` держит границу: кадр 511 —
столбец 0, кадр 512 — уже первый.

## Кэш и его отпечаток

Отпечаток = размер файла + время изменения в наносекундах. Дёшево читается и меняется при любом
перекодировании, ретегировании или замене файла — то есть ровно тогда, когда старый конверт
описывает другой звук. Формат файла: `DJWAVE01`, отпечаток, частота, размер столбца, число столбцов,
затем пары `min/max` в i16 (точность 1/32767 — для картинки избыточна).

Кэш лежит в `$XDG_CACHE_HOME/hauler-dj/peaks`, никогда в коллекции. Имя файла включает разрешение:
грубый конверт не может быть выдан там, где попросили тонкий.

## Проверено

7 тестов на реальных фикстурах (`tone-1s-44100.flac`, `silence-then-tone-2s-44100.flac`):

| Тест | Что держит |
|---|---|
| `the_envelope_describes_the_file_at_a_fixed_timebase` | 1 с при 44,1 кГц — 86–87 столбцов по 512 кадров, ровный конверт у тона |
| `the_timebase_maps_a_playhead_to_the_right_column` | граница 511/512, за концом — последний столбец |
| `silence_is_flat_and_a_tone_is_not` | тишина < 0,01, тон > 0,3 в нужных местах файла |
| `the_cache_returns_what_it_stored` | второй вызов не декодирует, данные совпадают в пределах шага i16 |
| `a_changed_fingerprint_invalidates_the_cache` | заменённый файл не получает старый конверт |
| `a_different_resolution_never_reuses_another_ones_entry` | 128 и 512 — разные продукты |
| `an_empty_envelope_is_harmless` | пустой конверт не паникует |

Живой прогон через протокол (10 с файла 48 кГц, 960 000 кадров):

```
waveform: {'path': '.../wave-track-c140af7e116af553-512.wave', 'frames_per_bucket': 512,
           'buckets': 1875, 'sample_rate': 48000}
file exists: True size: 7556     # 56 байт заголовка + 1875 * 4
```

1875 = 960 000 / 512 — ровно, без потерь на хвосте.

## Отрисовка

`qml/views/WaveformView.qml` рисует конверт Canvas'ом: по одному столбцу на пиксель, при избытке
столбцов берутся крайние значения группы (иначе трёхминутный трек превратился бы в шум). Плейхед
ставится как `source_frame / frames_per_bucket / columns * width` — из кадра, который присылает
движок, а не из локального таймера.

Чтение файла — `apps/dj-ui/src/Waveform.cpp`: разбор заголовка `DJWAVE01`, проверка длины (объявлено
столбцов против фактических), отказ чужому файлу с сообщением в интерфейсе.

Путь проверяется в гейте целиком — движок анализирует файл, кладёт `.wave`, публикует ссылку, UI
читает:

```
dj-ui: deck A is ready: track
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz
```

282 = 3 с × 48 000 / 512 = 281,25 — округление вверх, хвост не потерян.

## Маркеры и зум

На волновой форме рисуются: петля (полоса и её края), hotcue-метки с номером слота и плейхед. Все
позиции считаются одной формулой — `frame / frames_per_bucket / columns`, то есть из кадров, которые
прислал движок. Той же формулой пользуется Rust (`Peaks::bucket_for`), и она покрыта тестами; QML
проверяется загрузкой сцены (любая ошибка в формулах даёт предупреждение Qt) и глазами владельца.

Зум — колесо мыши (пивот под курсором), двойной клик сбрасывает. Он **пересобирает тот же конверт**:
при отдалении несколько столбцов схлопываются в пиксель с сохранением крайних значений, при
приближении столбец занимает несколько пикселей и показывает свою истинную протяжённость. Детали он
не выдумывает: когда столбцов становится меньше пикселя, панель пишет «envelope limit» — тонкий
конверт должен запросить у движка, это следующий шаг.

Покрытие проверяется в гейте: конверт обязан описать все кадры трека.

```
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz, covering 144384 of 144000 frames
```

144384 = 282 × 512 ≥ 144 000 — последний столбец неполный, но покрытие полное, поэтому метка у самого
конца трека не уедет за край.

## Что осталось в A07
- Зум: грубый и тонкий конверты уже независимы в кэше, но UI просит только обзорный.
- Фоновая подготовка: анализ идёт в потоке загрузчика, то есть блокирует следующую загрузку до
  окончания; отдельная очередь для библиотеки — это A08.
- Маркеры биений (нужен анализ BPM — DJP-MEDIA-006) и stem lanes (R2) — не сделаны.
- Тонкий конверт по зуму не запрашивается у движка: приближение ограничено обзорным разрешением.

## Дефект: одна волновая форма на две деки

Владелец заметил: загрузка в деку A рисовала форму и на деке B. Причина — `Waveform` был
QML-синглтоном, то есть **один читатель на всё приложение**; оба вида писали в него, побеждал
последний, и обе панели рисовали его содержимое.

Исправлено: `WaveformEnvelope` — зарегистрированный тип, каждый вид создаёт свой экземпляр
(`WaveformEnvelope { id: envelope }`). Синглтон в QML нельзя инстанциировать, поэтому смоук-тест
теперь ловит такую ошибку сам: сцена просто не загрузится.

Проверка независимости в гейте — две деки, два файла разной длины:

```
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz, covering 144384 of 144000 frames
dj-ui: sent Load(B) as command 2
dj-ui: two envelopes, kept apart: A 282 columns, B 563 columns
```

282 = 3 с × 48 000 / 512, 563 = 6 с × 48 000 / 512. Совпадение столбцов было бы признаком того, что
читатель снова общий, и проверка падает именно на этом условии.

## Проверка владельцем (2026-11-05)

- Волновые формы больше не перепутываются: загрузка в деку A не рисует форму на деке B.
- Одновременное воспроизведение двух дек на настоящем устройстве — «работает хорошо» на слух.

Второй пункт — это приёмка DJP-MIX-001, которую ни один headless-тест заменить не может: тесты
проверяют маршрутизацию и лимитер по числам, но «звучит правильно» подтверждается только слухом.

## Прокрутка: плейхед в центре, зум вокруг него

По замечанию владельца вид переделан из «показать весь трек» в прокручивающуюся полосу:

- точка воспроизведения всегда в горизонтальном центре; волна движется под ней, а не плейхед по
  волне — так глаз держит одно место, как на CDJ;
- зум (колесо, двойной клик — сброс) меняет только видимую долю трека, поэтому пивот у него один и
  тот же — плейхед; отдельной логики «зум под курсором» больше нет;
- области до первого кадра и после последнего закрашиваются **отдельным цветом**
  (`--waveform-outside-color`, по умолчанию фон полосы `#101317`): у начала трека левая половина
  полосы честно показывает, что там ничего нет, а не тишину внутри трека;
- порядок отрисовки: фон → зоны вне трека → осевая линия → волна (только столбцы в окне) → петля →
  hotcue → плейхед.

Проверки: неверный цвет отвергается с кодом 2 (`dj-ui: not-a-colour is not a colour`), корректный
проходит через QML без предупреждений — оба случая в гейте (`scripts/ui.sh --smoke`).

## Цветная волновая форма и выбор вида

Вид настраивается: `--waveform-style coloured` (по умолчанию) или `plain`. Цветной режим не
раскрашивает пики произвольно — он опирается на данные, которые считает анализ.

`dj-analysis` теперь хранит в каждом столбце, кроме экстремумов, RMS двух отфильтрованных копий
микса: ниже 220 Гц и выше 3,5 кГц (однополюсные фильтры, без FFT — на этом разрешении спектр дороже
картинки). Файл конверта стал `DJWAVE02`, шесть байт на столбец, уровни с квадратичным сжатием.

Проверки:

| Тест | Что держит |
|---|---|
| `the_bands_separate_bass_from_treble` | тон 60 Гц читается как бас (`low` втрое выше `high`), тон 9 кГц — наоборот |
| `the_cache_keeps_the_bands` | уровни переживают запись в файл с точностью до шага u8 |

Чтение в UI проверяется в гейте — конверт обязан прийти с уровнями, иначе цветной режим молча
деградировал бы до одноцветного:

```
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz, covering 144384 of 144000 frames;
        bands low 0.332 high 0.071
```

Оба вида и неверное значение флага (`exit 2`) прогоняются в `scripts/ui.sh --smoke`.

## Муар на промежуточных увеличениях

Причина была в способе рисования, а не в данных: конверт рисовался по столбцам с дробной
координатой `x`, и при некоторых масштабах соседние штрихи попадали в один пиксель или пропускали
соседний. Регулярность этого пропуска и читалась как муар.

Теперь агрегация в один пиксель делается **до** рисования, в C++ (`Waveform::profile`): на окно
приходится ровно `width` записей, каждая владеет непрерывным диапазоном столбцов, диапазоны стыкуются
без щелей и наложений по построению (граница пикселя `p+1` — это конец диапазона пикселя `p`). QML
рисует по одному прямоугольнику на пиксель с целочисленной координатой.

Проверка — свойство, а не глаз: в гейте профиль строится для 640, 901 и 1280 пикселей, и он обязан
покрыть все столбцы трека ровно один раз.

```
dj-ui: profile tiles the track at 640, 901 and 1280 px
```

Первый прогон этой проверки упал, и правильно: я считал покрытие по пикселям, а при 640 пикселях на
282 столбца каждый столбец повторяется, и «покрыто» выходило 640 из 282. Считать надо различные
столбцы — исправлено, проверка стала осмысленной.

## Палитра (предыдущая версия, две полосы)

Три цвета, настраиваемые: `--waveform-band-colors НИЗ,СРЕД,ВЕРХ`, по умолчанию `#e0512f,#e8b53a,#dfeaf7`
(тёплый бас, янтарная середина, холодный верх). Между соседними цветами интерполяция по отношению

Это **наша реконструкция** общей схемы DJ-софта, а не палитра Traktor: ADR-001 запрещает брать их
графику и ресурсы, а описания их цветов найти не удалось — обе страницы поддержки NI отдают 404,
поиск в окружении не настроен.

## Почему волна была одного цвета

Сообщение владельца: «вся волна рисуется просто зелёным». Причина не в детектировании — полосы
считались правильно, — а в том, **чем** их сравнивали между собой.

Полоса середины занимает 220 Гц … 3,5 кГц, это примерно четыре октавы; бас — полторы, верх — ещё
четыре, но с малым количеством энергии в обычной музыке. В любой музыке абсолютная энергия середины
самая большая, поэтому смесь цветов по сырым энергиям почти всегда давала зелёный.

Цвет теперь строится по отношению **к самому треку**: анализ считает медиану каждой полосы по всему
файлу и пишет её в заголовок конверта, а рендер делит уровень столбца на эту медиану. Тогда цвет
показывает, чем столбец отличается от трека: бочка — красная, хэт — холодный, — а не «сколько в нём
энергии». Веса возводятся в куб, чтобы лидер забирал столбец, и сглаживаются по пяти соседним
столбцам: иначе у столбцов, где полосы почти равны, цвет дёргался бы между красным, зелёным и
фиолетовым от пикселя к пикселю.

Формат конверта — `DJWAVE04` (три медианы в заголовке, заголовок 59 байт). Заголовок 56 байт был
ошибкой сразу после добавления медиан: чтение столбцов начиналось на три байта раньше и брало
медианы за данные.

Проверки:

- `the_colour_follows_the_balance_not_the_raw_energy` — файл, у которого первая секунда с перевесом
  середины, вторая с перевесом верха; в сырых энергиях середина выигрывает в обеих половинах (именно
  поэтому всё было зелёным), а после нормировки половины читаются по-разному;
- в гейте прогоняются два файла: тон 440 Гц (обязана доминировать середина) и синтезированные барабаны
  `drums-8s-48000.wav` (обязаны доминировать минимум две полосы, иначе картинка снова одноцветная).

```
dj-ui: colour spread over the track: low 21% mid 39% high 40%   (тон 440 Гц)
dj-ui: colour spread over the track: low 87% mid 2%  high 11%   (барабаны: бочка и хэт)
dj-ui: 2 bands claim a tenth of the columns
```

Требование «минимум две полосы», а не «все три»: в синтезированных барабанах середины почти нет, и
требовать её значило бы подогнать порог под фикстуру, а не под требование.

## Итоговая раскладка цвета

Промежуточная версия смешивала три цвета в один пиксель. Среднее из красного, зелёного и
фиолетового — серо-зелёный, поэтому «слишком много зелёного» было не перекосом данных, а
следствием смешивания: любая пара разных цветов, смешанная поровну, теряет цвет.

Теперь:

- **высота волны** — амплитуда огибающей, то есть громкость (как и ожидалось);
- **цвет столбца** — одна краска на столбец: берётся полоса-лидер и полоса-вторая, смешиваются в
  их отношении. Переход получается непрерывным, а промежуточные смеси дают оранжевый и жёлтый —
  ровно там, где бас переходит в середину;
- **доли полос** считаются от медианы каждой полосы по всему треку. Из-за этого ни одна полоса не
  может захватить картинку в силу своей ширины: по всему треку каждая в среднем единица, и цвет
  показывает только то, что меняется локально.

Проверка по барабанам (симуляция той же формулы на конверте, которую я прогнал численно, потому что
глазами картинку в этом окружении не посмотреть):

| Оттенок | Доля столбцов |
|---|---|
| 0–30° красный | 46% |
| 30–60° оранжевый и жёлтый | 26% |
| 240–270° синий и фиолетовый | 16% |
| 120–180° зелёный | 6% |

Бочка даёт красный и оранжевый, хэт — фиолетовый. Раньше всё это усреднялось в один зелёный.

## Найденный дефект рядом

Второй клиент, подключившийся к движку сразу после двухдечной загрузки, получил пустую деку: поток
загрузчика ещё был занят, и `Load` второго клиента не отработал. Проверка цвета теперь поднимает
свой движок, чтобы не зависеть от этого. Сам дефект — отдельная задача: он про повторное
подключение, а не про волну.

## Раскладка по громкости полос (по указанию владельца)

Владелец сформулировал правило прямо: брать ярко-красный, жёлтый и ярко-синий за эталоны, сравнивать
громкость полос на участке, самую громкую полосу ставить на полную яркость, остальные подмешивать
пропорционально их громкости.

Реализовано буквально:

```
вес_полосы = громкость_полосы / max(громкость полос столбца)
цвет       = Σ (вес_i / Σвес) · эталон_i
```

То есть лидер всегда на полной яркости своего эталона, а остальные разбавляют его тем сильнее, чем
ближе их громкость к лидеру. Никакой нормировки на средние по треку больше нет: картинка следует за
музыкой в этот момент.

Цвет теперь считается **в одном месте** — `Waveform::pixelColor` в C++, — а QML только закрашивает
прямоугольник полученным цветом. Это важно, потому что обсуждать цвет по описанию бессмысленно: нужно
мерить то, что нарисовано.

Добавлен режим, который рисует волну в файл тем же кодом:

```
nix develop --command bash scripts/waveform-png.sh track.flac /tmp/wave.png
```

(`dj-headless waveform` считает конверт, `dj-ui --waveform-png` рисует PNG; нужен только путь к
аудиофайлу.)

### Измерение на синтезированных барабанах

`docs/qa/evidence/A07/waveform-drums.png` — та самая картинка. Разбор пикселей:

| Оттенок | Доля закрашенных пикселей |
|---|---|
| красный | 66% |
| синий | 34% |
| жёлтый | 0% |

Жёлтого нет не потому, что он потерялся: в синтезированных барабанах середина почти отсутствует
(бочка 60 Гц, хэт 9 кГц), и лидером она не становится нигде. На реальном треке середина участвует,
и цвет должен проходить через жёлтый.

### Как проверить на настоящей музыке

```
nix develop --command bash scripts/waveform-png.sh "/путь/к/треку.flac" /tmp/wave.png
```

Файл — ровно то, что покажет дека. Если раскладка не нравится, менять надо одно число: соотношение
в `pixelColor`, а не рисование.

## Четвёртая итерация: отклонение от своего обычного уровня

Третья итерация красила по сырой громкости — и владелец увидел сплошной красный. Причина в том, что
сравнение с нулём всегда выигрывает та полоса, которая шире по частоте: сначала середина дала «всю
волну зелёной», потом бас — «всю волну красной». Обе ошибки — одна и та же.

Теперь полоса сравнивается со своим обычным уровнем в этом треке: бочка красная не потому, что бас
громкий вообще, а потому что он громче, чем обычно в этом треке. Обычный уровень берётся по столбцам,
где трек играет (не ниже четверти пика): медиана по всем столбцам занижена тишиной между ударами, и
редкая полоса выглядит огромной, как только звучит.

Измерения (`--waveform-png` печатает их вместе с картинкой):

| Материал | Обычные уровни (низ/сред/верх) | Оттенки |
|---|---|---|
| синтезированные барабаны | 0,2215 / 0,0572 / 0,0062 | красный 195, оранжевый 38, жёлтый 4, синий 74 |
| розовый шум | 0,1034 / 0,0912 / 0,0630 | красный 577, оранжевый 274, жёлтый 232, синий 113, фиолетовый 4 |

До правки медиана по всем столбцам давала обычный низ 0,0138 и почти сплошное красное. Розовый шум
(наклон спектра как у музыки) даёт все пять оттенков: ни одна полоса не захватывает картинку по своей
ширине.

Проверка усилений: `--waveform-band-gain 1,2,3` на барабанах меняет раскладку на красный 169,
оранжевый 52, жёлтый 12, синий 74 — усиления действительно управляют тем, какой полосы больше видно,
и подбираются под материал без пересборки.

Реального трека в песочнице нет, поэтому следующая настройка — по данным владельца:

```
nix develop --command bash scripts/waveform-png.sh "/путь/к/треку.flac" /tmp/wave.png
```

Команда печатает строку `dj-ui: hues ...` и обычные уровни полос. Если на треке с басом и хэтами
преобладает красный, по этой строке видно, во сколько раз поднимать усиления середины и верха.

## Пятая итерация: RGB-кроссовер по рекомендациям владельца

Владелец положил в `tmp/wave-form.md` описание того, как это делают библиотеки визуализации и
DJ-программы. Схема простая и я реализовал её буквально:

1. **Полосы:** бас 20–250 Гц, середина 250–4000 Гц, верх 4000–20000 Гц (пороги сдвинуты с 220/3500).
2. **Агрегация:** RMS каждой полосы на столбец, плюс пиковая огибающая для высоты.
3. **Привязка к цвету:** полосы управляют каналами R, G, B напрямую и складываются. Бас + середина =
   оранжевый, середина + верх = бирюзовый, всё сразу = бледный/белый.
4. **Нормализация:** самая сильная полоса столбца заполняет свой канал целиком, остальные идут
   пропорционально; база сравнения — обычный уровень полосы в этом треке, а не ноль.
5. **Высота:** самый громкий столбец трека занимает всю высоту, остальные масштабируются (раньше
   тихий трек выглядел тонкой линией).

Ключевое отличие от предыдущих попыток: полосы больше не соревнуются за «единственный цвет столбца».
Каждая всегда вкладывается в свой канал, поэтому схема не может выродиться в один оттенок — а именно
этим заканчивались все четыре предыдущие попытки (вся зелень, вся краснота).

Измерения (`--waveform-png` печатает вместе с картинкой):

| Материал | Оттенки |
|---|---|
| синтезированные барабаны (бочка + хэт) | белый 35, красный 12, оранжевый 117, жёлтый 73, синий 74 |
| розовый шум | белый 1064, красный 69, оранжевый 41, жёлтый 3, бирюзовый 23 |

Барабаны дают оранжевый и жёлтый (бас с серединой), синий на хэтах. Розовый шум — почти весь белый,
ровно как в документе: плотный широкополосный материал стремится к белому.

`docs/qa/evidence/A07/waveform-drums.png` — картинка, по которой это измерялось.

## Шестая итерация: оттенок по спектральному положению, сверено со скриншотом

Присланная статистика реального трека (`white 635, cyan 374, yellow 83, orange 68`) показала, что
аддитивная схема R/G/B на музыке уходит в белый и бирюзовый. Прежде чем менять её ещё раз, я измерил
сам эталон: взял скриншот TRAKTOR PRO 4 из `tmp/`, вырезал полосу волны и посмотрел, как там
расположены цвета.

Что оказалось:

- **столбец окрашен одним цветом сверху донизу** — не слоями и не смешением каналов;
- цвета идут по кругу: красный, оранжевый, жёлтый, зелёный, бирюзовый, синий, фиолетовый;
- распределение по полосе: зелёный 31%, красный 26%, оранжевый 13%, бирюзовый 11%, синий 11%,
  фиолетовый 4%, жёлтый 4%.

Значит, цвет — не «какой полосы больше», а **где на частотной оси лежит энергия**: непрерывный
оттенок от низких к высоким. Так и реализовано:

```
доли полос (абсолютная громкость) → положение на лог-оси 20 Гц … 20 кГц
центры полос: бас 0,181 · середина 0,566 · верх 0,884
оттенок: 0,00 → 3°, 0,30 → 14°, 0,45 → 50°, 0,60 → 120°, 0,75 → 178°, 0,88 → 232°, 1,00 → 275°
насыщенность: 0,35 … 1,0 по доле сильнейшей полосы
```

Проверка на синтезированной «песне» с тремя секциями (аккорды → плюс хэт → плюс бочка и бас), цвета
по секциям:

| Секция | Цвета |
|---|---|
| 0–4 с, только аккорды | жёлтый 100% |
| 4–8 с, добавлен хэт | жёлтый 91%, зелёный 9% |
| 8–12 с, добавлены бочка и бас | оранжевый 99% |

То есть цвет меняется вместе с музыкой, а не застывает. На барабанах (бочка + хэт) — красный 237,
бирюзовый 74: бочка красная, хэт холодный.

Абсолютная громкость вместо «против обычного уровня» — важная деталь: ровная басовая линия громкая
всегда, и нормировка на её же среднее делала её незаметной там, где она должна быть красной. Именно
из-за этого на реальном треке красного было 3 столбца из 1182.

## Седьмая итерация: фильтры были пологими

На реальном треке после шестой итерации вышло `red 741, orange 273, yellow 58, green 110` — красный
появился, но холодные цвета пропали совсем. При разборе оказалось, что причина глубже раскраски.

Разделение на полосы делалось **однополюсными** фильтрами: у такого фильтра срез всего 6 дБ на октаву,
поэтому на 1 кГц фильтр 250 Гц пропускает ещё около трети энергии. «Бас» содержал середину, был
громким в каждом столбце любого трека, и никакая раскраска не могла отличить бочку от аккорда.

Что сделано:

- фильтры стали четвёртого порядка (два каскада), срез около −24 дБ на октаву;
- каскад из двух одинаковых секций даёт −3 дБ на 0,6436 собственной частоты секции, поэтому частота
  секции ставится в 1,554 раза выше нужной — иначе срез уезжает вниз и середина протекает в верх;
- каждая полоса сравнивается со своим громким уровнем (95-й процентиль по треку), а не с абсолютной
  энергией: верха в любой музыке несут долю энергии баса, и по абсолютной шкале они никогда не
  доходили до синего;
- оттенок по-прежнему один на столбец и идёт по кругу, положение — на лог-оси частот.

Измерения после правки:

| Материал | Оттенки |
|---|---|
| барабаны (бочка + хэт) | красный 56, оранжевый 177, жёлтый 4, бирюзовый 63, синий 11 |
| «песня»: аккорды → +хэт → +бочка и бас | 0–4 с зелёный 100%; 4–8 с зелёный 91% + бирюзовый и синий 9%; 8–12 с зелёный 56%, жёлтый 41% |
| розовый шум | зелёный 1196 |

Тест `the_colour_follows_the_balance_not_the_raw_energy` поймал ошибку калибровки каскада: при
неверной частоте секции середина протекала в верхнюю полосу, и «верх» был 0,19 там, где должно быть
0,03. Без этого теста пологие фильтры остались бы незамеченными ещё на несколько итераций.

## Восьмая итерация: контраст шкалы

После седьмой итерации реальный трек дал `red 12, orange 401, yellow 333, green 386, cyan 50` —
цвета появились, но сбились в оранжево-жёлто-зелёную середину: крайних участков шкалы почти нет.
Причина арифметическая: доли трёх полос близки друг к другу, поэтому центр тяжести почти всегда
попадает в середину оси.

Что изменено:

- доли возводятся в степень 1,5 перед нормировкой — лидирующая полоса подтягивает оттенок к своей
  части круга, не скрывая остальные;
- центры полос на оси разнесены: 0,14 / 0,52 / 0,90 вместо 0,18 / 0,57 / 0,88.

Измерения после правки:

| Материал | Оттенки |
|---|---|
| барабаны (бочка + хэт) | красный 209, оранжевый 28, синий 74 |
| «песня» (аккорды + хэт + бочка/бас) | зелёный 853, оранжевый 153, жёлтый 149, бирюзовый 25, синий 20 |
| розовый шум | зелёный 1141, жёлтый 33 |

На барабанах бочка стала красной (67% столбцов), хэт — синим: крайние участки шкалы достижимы.

## Девятая итерация: границы полос

Гистограмма владельца после восьмой итерации — `red 328, orange 390, yellow 131, green 258, cyan 73,
blue 2` — уже близка к эталону по тёплым цветам, но холодных 6% против 22% в скриншоте Traktor.
Причина в верхней границе: полоса верха начиналась с 4 кГц, а тарелки, сибилянты и «воздух» лежат
ниже — их энергия попадала в середину.

Границы сдвинуты к обычному DJ-делению: 200 Гц и 2500 Гц вместо 250 и 4000. Центры полос на оси:
0,10 / 0,48 / 0,92.

Формат конверта — `DJWAVE10`: старые файлы пересчитываются, потому что изменился сам анализ, а не
только раскраска.

Заодно переписан тест `the_colour_follows_the_balance_not_the_raw_energy`. Прежняя формулировка
требовала перевеса середины над верхом в 2 раза **после** нормировки на медиану по всему файлу, а
медиана лежит между половинами, и при сдвиге границ запас стал 1,14 против нужных 1,26. Теперь
маржи проверяются на сырых уровнях (там они физические и устойчивые), а нормированные значения
проверяются только на то, что половины действительно читаются по-разному.

Измерения после сдвига:

| Материал | Оттенки |
|---|---|
| барабаны | красный 221, оранжевый 16, синий 74 |
| «песня» (аккорды + хэт + бочка/бас) | зелёный 796, оранжевый 211, жёлтый 117, бирюзовый 48, синий 16, красный 12 |
| розовый шум | зелёный 1106, жёлтый 56, бирюзовый 26 |
