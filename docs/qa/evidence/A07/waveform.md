# Волновые формы: конверт и кэш (A07, часть 1)

`crates/dj-analysis` больше не заглушка: конверт (min/max на столбец), кэш на диске с отпечатком
файла, ссылка на конверт в состоянии деки.

## Время — в кадрах источника

Столбец `n` покрывает кадры `[n * frames_per_bucket, (n + 1) * frames_per_bucket)`. Поэтому
плейхед ставится по `frame / frames_per_bucket` без масштабных поправок — это и есть требование
DJP-MEDIA-003. Тест `the_timebase_maps_a_playhead_to_the_right_column` держит границу: кадр 511 —
столбец 0, кадр 512 — уже первый.

## Кэш и его отпечаток

Отпечаток = размер файла + время изменения в наносекундах. Дёшево читается и меняется при любом
перекодировании, ретегировании или замене файла — то есть ровно тогда, когда старый конверт
описывает другой звук. Формат файла: `DJWAVE01`, отпечаток, частота, размер столбца, число столбцов,
затем пары `min/max` в i16 (точность 1/32767 — для картинки избыточна).

Кэш лежит в `$XDG_CACHE_HOME/hauler-dj/peaks`, никогда в коллекции. Имя файла включает разрешение:
грубый конверт не может быть выдан там, где попросили тонкий.

## Проверено

7 тестов на реальных фикстурах (`tone-1s-44100.flac`, `silence-then-tone-2s-44100.flac`):

| Тест | Что держит |
|---|---|
| `the_envelope_describes_the_file_at_a_fixed_timebase` | 1 с при 44,1 кГц — 86–87 столбцов по 512 кадров, ровный конверт у тона |
| `the_timebase_maps_a_playhead_to_the_right_column` | граница 511/512, за концом — последний столбец |
| `silence_is_flat_and_a_tone_is_not` | тишина < 0,01, тон > 0,3 в нужных местах файла |
| `the_cache_returns_what_it_stored` | второй вызов не декодирует, данные совпадают в пределах шага i16 |
| `a_changed_fingerprint_invalidates_the_cache` | заменённый файл не получает старый конверт |
| `a_different_resolution_never_reuses_another_ones_entry` | 128 и 512 — разные продукты |
| `an_empty_envelope_is_harmless` | пустой конверт не паникует |

Живой прогон через протокол (10 с файла 48 кГц, 960 000 кадров):

```
waveform: {'path': '.../wave-track-c140af7e116af553-512.wave', 'frames_per_bucket': 512,
           'buckets': 1875, 'sample_rate': 48000}
file exists: True size: 7556     # 56 байт заголовка + 1875 * 4
```

1875 = 960 000 / 512 — ровно, без потерь на хвосте.

## Отрисовка

`qml/views/WaveformView.qml` рисует конверт Canvas'ом: по одному столбцу на пиксель, при избытке
столбцов берутся крайние значения группы (иначе трёхминутный трек превратился бы в шум). Плейхед
ставится как `source_frame / frames_per_bucket / columns * width` — из кадра, который присылает
движок, а не из локального таймера.

Чтение файла — `apps/dj-ui/src/Waveform.cpp`: разбор заголовка `DJWAVE01`, проверка длины (объявлено
столбцов против фактических), отказ чужому файлу с сообщением в интерфейсе.

Путь проверяется в гейте целиком — движок анализирует файл, кладёт `.wave`, публикует ссылку, UI
читает:

```
dj-ui: deck A is ready: track
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz
```

282 = 3 с × 48 000 / 512 = 281,25 — округление вверх, хвост не потерян.

## Маркеры и зум

На волновой форме рисуются: петля (полоса и её края), hotcue-метки с номером слота и плейхед. Все
позиции считаются одной формулой — `frame / frames_per_bucket / columns`, то есть из кадров, которые
прислал движок. Той же формулой пользуется Rust (`Peaks::bucket_for`), и она покрыта тестами; QML
проверяется загрузкой сцены (любая ошибка в формулах даёт предупреждение Qt) и глазами владельца.

Зум — колесо мыши (пивот под курсором), двойной клик сбрасывает. Он **пересобирает тот же конверт**:
при отдалении несколько столбцов схлопываются в пиксель с сохранением крайних значений, при
приближении столбец занимает несколько пикселей и показывает свою истинную протяжённость. Детали он
не выдумывает: когда столбцов становится меньше пикселя, панель пишет «envelope limit» — тонкий
конверт должен запросить у движка, это следующий шаг.

Покрытие проверяется в гейте: конверт обязан описать все кадры трека.

```
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz, covering 144384 of 144000 frames
```

144384 = 282 × 512 ≥ 144 000 — последний столбец неполный, но покрытие полное, поэтому метка у самого
конца трека не уедет за край.

## Что осталось в A07
- Зум: грубый и тонкий конверты уже независимы в кэше, но UI просит только обзорный.
- Фоновая подготовка: анализ идёт в потоке загрузчика, то есть блокирует следующую загрузку до
  окончания; отдельная очередь для библиотеки — это A08.
- Маркеры биений (нужен анализ BPM — DJP-MEDIA-006) и stem lanes (R2) — не сделаны.
- Тонкий конверт по зуму не запрашивается у движка: приближение ограничено обзорным разрешением.

## Дефект: одна волновая форма на две деки

Владелец заметил: загрузка в деку A рисовала форму и на деке B. Причина — `Waveform` был
QML-синглтоном, то есть **один читатель на всё приложение**; оба вида писали в него, побеждал
последний, и обе панели рисовали его содержимое.

Исправлено: `WaveformEnvelope` — зарегистрированный тип, каждый вид создаёт свой экземпляр
(`WaveformEnvelope { id: envelope }`). Синглтон в QML нельзя инстанциировать, поэтому смоук-тест
теперь ловит такую ошибку сам: сцена просто не загрузится.

Проверка независимости в гейте — две деки, два файла разной длины:

```
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz, covering 144384 of 144000 frames
dj-ui: sent Load(B) as command 2
dj-ui: two envelopes, kept apart: A 282 columns, B 563 columns
```

282 = 3 с × 48 000 / 512, 563 = 6 с × 48 000 / 512. Совпадение столбцов было бы признаком того, что
читатель снова общий, и проверка падает именно на этом условии.

## Проверка владельцем (2026-11-05)

- Волновые формы больше не перепутываются: загрузка в деку A не рисует форму на деке B.
- Одновременное воспроизведение двух дек на настоящем устройстве — «работает хорошо» на слух.

Второй пункт — это приёмка DJP-MIX-001, которую ни один headless-тест заменить не может: тесты
проверяют маршрутизацию и лимитер по числам, но «звучит правильно» подтверждается только слухом.

## Прокрутка: плейхед в центре, зум вокруг него

По замечанию владельца вид переделан из «показать весь трек» в прокручивающуюся полосу:

- точка воспроизведения всегда в горизонтальном центре; волна движется под ней, а не плейхед по
  волне — так глаз держит одно место, как на CDJ;
- зум (колесо, двойной клик — сброс) меняет только видимую долю трека, поэтому пивот у него один и
  тот же — плейхед; отдельной логики «зум под курсором» больше нет;
- области до первого кадра и после последнего закрашиваются **отдельным цветом**
  (`--waveform-outside-color`, по умолчанию фон полосы `#101317`): у начала трека левая половина
  полосы честно показывает, что там ничего нет, а не тишину внутри трека;
- порядок отрисовки: фон → зоны вне трека → осевая линия → волна (только столбцы в окне) → петля →
  hotcue → плейхед.

Проверки: неверный цвет отвергается с кодом 2 (`dj-ui: not-a-colour is not a colour`), корректный
проходит через QML без предупреждений — оба случая в гейте (`scripts/ui.sh --smoke`).

## Цветная волновая форма и выбор вида

Вид настраивается: `--waveform-style coloured` (по умолчанию) или `plain`. Цветной режим не
раскрашивает пики произвольно — он опирается на данные, которые считает анализ.

`dj-analysis` теперь хранит в каждом столбце, кроме экстремумов, RMS двух отфильтрованных копий
микса: ниже 220 Гц и выше 3,5 кГц (однополюсные фильтры, без FFT — на этом разрешении спектр дороже
картинки). Файл конверта стал `DJWAVE02`, шесть байт на столбец, уровни с квадратичным сжатием.

Проверки:

| Тест | Что держит |
|---|---|
| `the_bands_separate_bass_from_treble` | тон 60 Гц читается как бас (`low` втрое выше `high`), тон 9 кГц — наоборот |
| `the_cache_keeps_the_bands` | уровни переживают запись в файл с точностью до шага u8 |

Чтение в UI проверяется в гейте — конверт обязан прийти с уровнями, иначе цветной режим молча
деградировал бы до одноцветного:

```
dj-ui: waveform loaded: 282 columns of 512 frames at 48000 Hz, covering 144384 of 144000 frames;
        bands low 0.332 high 0.071
```

Оба вида и неверное значение флага (`exit 2`) прогоняются в `scripts/ui.sh --smoke`.

## Муар на промежуточных увеличениях

Причина была в способе рисования, а не в данных: конверт рисовался по столбцам с дробной
координатой `x`, и при некоторых масштабах соседние штрихи попадали в один пиксель или пропускали
соседний. Регулярность этого пропуска и читалась как муар.

Теперь агрегация в один пиксель делается **до** рисования, в C++ (`Waveform::profile`): на окно
приходится ровно `width` записей, каждая владеет непрерывным диапазоном столбцов, диапазоны стыкуются
без щелей и наложений по построению (граница пикселя `p+1` — это конец диапазона пикселя `p`). QML
рисует по одному прямоугольнику на пиксель с целочисленной координатой.

Проверка — свойство, а не глаз: в гейте профиль строится для 640, 901 и 1280 пикселей, и он обязан
покрыть все столбцы трека ровно один раз.

```
dj-ui: profile tiles the track at 640, 901 and 1280 px
```

Первый прогон этой проверки упал, и правильно: я считал покрытие по пикселям, а при 640 пикселях на
282 столбца каждый столбец повторяется, и «покрыто» выходило 640 из 282. Считать надо различные
столбцы — исправлено, проверка стала осмысленной.

## Палитра (предыдущая версия, две полосы)

Три цвета, настраиваемые: `--waveform-band-colors НИЗ,СРЕД,ВЕРХ`, по умолчанию `#e0512f,#e8b53a,#dfeaf7`
(тёплый бас, янтарная середина, холодный верх). Между соседними цветами интерполяция по отношению
уровней полос.

Это **наша реконструкция** общей схемы DJ-софта, а не палитра Traktor: ADR-001 запрещает брать их
графику и ресурсы, а описания их цветов найти не удалось — обе страницы поддержки NI отдают 404,
поиск в окружении не настроен.

## Почему волна была одного цвета

Сообщение владельца: «вся волна рисуется просто зелёным». Причина не в детектировании — полосы
считались правильно, — а в том, **чем** их сравнивали между собой.

Полоса середины занимает 220 Гц … 3,5 кГц, это примерно четыре октавы; бас — полторы, верх — ещё
четыре, но с малым количеством энергии в обычной музыке. В любой музыке абсолютная энергия середины
самая большая, поэтому смесь цветов по сырым энергиям почти всегда давала зелёный.

Цвет теперь строится по отношению **к самому треку**: анализ считает медиану каждой полосы по всему
файлу и пишет её в заголовок конверта, а рендер делит уровень столбца на эту медиану. Тогда цвет
показывает, чем столбец отличается от трека: бочка — красная, хэт — холодный, — а не «сколько в нём
энергии». Веса возводятся в куб, чтобы лидер забирал столбец, и сглаживаются по пяти соседним
столбцам: иначе у столбцов, где полосы почти равны, цвет дёргался бы между красным, зелёным и
фиолетовым от пикселя к пикселю.

Формат конверта — `DJWAVE04` (три медианы в заголовке, заголовок 59 байт). Заголовок 56 байт был
ошибкой сразу после добавления медиан: чтение столбцов начиналось на три байта раньше и брало
медианы за данные.

Проверки:

- `the_colour_follows_the_balance_not_the_raw_energy` — файл, у которого первая секунда с перевесом
  середины, вторая с перевесом верха; в сырых энергиях середина выигрывает в обеих половинах (именно
  поэтому всё было зелёным), а после нормировки половины читаются по-разному;
- в гейте прогоняются два файла: тон 440 Гц (обязана доминировать середина) и синтезированные барабаны
  `drums-8s-48000.wav` (обязаны доминировать минимум две полосы, иначе картинка снова одноцветная).

```
dj-ui: colour spread over the track: low 21% mid 39% high 40%   (тон 440 Гц)
dj-ui: colour spread over the track: low 87% mid 2%  high 11%   (барабаны: бочка и хэт)
dj-ui: 2 bands claim a tenth of the columns
```

Требование «минимум две полосы», а не «все три»: в синтезированных барабанах середины почти нет, и
требовать её значило бы подогнать порог под фикстуру, а не под требование.

## Итоговая раскладка цвета

Промежуточная версия смешивала три цвета в один пиксель. Среднее из красного, зелёного и
фиолетового — серо-зелёный, поэтому «слишком много зелёного» было не перекосом данных, а
следствием смешивания: любая пара разных цветов, смешанная поровну, теряет цвет.

Теперь:

- **высота волны** — амплитуда огибающей, то есть громкость (как и ожидалось);
- **цвет столбца** — одна краска на столбец: берётся полоса-лидер и полоса-вторая, смешиваются в
  их отношении. Переход получается непрерывным, а промежуточные смеси дают оранжевый и жёлтый —
  ровно там, где бас переходит в середину;
- **доли полос** считаются от медианы каждой полосы по всему треку. Из-за этого ни одна полоса не
  может захватить картинку в силу своей ширины: по всему треку каждая в среднем единица, и цвет
  показывает только то, что меняется локально.

Проверка по барабанам (симуляция той же формулы на конверте, которую я прогнал численно, потому что
глазами картинку в этом окружении не посмотреть):

| Оттенок | Доля столбцов |
|---|---|
| 0–30° красный | 46% |
| 30–60° оранжевый и жёлтый | 26% |
| 240–270° синий и фиолетовый | 16% |
| 120–180° зелёный | 6% |

Бочка даёт красный и оранжевый, хэт — фиолетовый. Раньше всё это усреднялось в один зелёный.

## Найденный дефект рядом

Второй клиент, подключившийся к движку сразу после двухдечной загрузки, получил пустую деку: поток
загрузчика ещё был занят, и `Load` второго клиента не отработал. Проверка цвета теперь поднимает
свой движок, чтобы не зависеть от этого. Сам дефект — отдельная задача: он про повторное
подключение, а не про волну.

## Реализация: FFT + перцептивные веса + HSV-форсирование

Третий заход на волну сделан с нуля по новой спецификации; прежняя фильтровая схема удалена
целиком. Отличие принципиальное: полосы считает **БПФ**, а не фильтры, и цвет не смешивается, а
приводится к чистому оттенку.

### Пайплайн

1. **Вход:** PCM, моно (усреднение стерео), частота из файла.
2. **Окна:** столбец конверта = окно анализа; размер БПФ — степень двойки от размера окна, окно
   Ханна (иначе тон, не кратный окну, светит во все полосы).
3. **Полосы по спектру:** бас 20–280 Гц, середина 280–3500 Гц, верх 3500–20000 Гц; в каждой —
   RMS амплитуд бинов, попавших в диапазон.
4. **Перцептивные веса:** `R = bass`, `G = mids × 1.5`, `B = treble × 2.5` — верх и середина несут
   меньше энергии, и без подъёма картинка выходит чисто красной.
5. **Экспоненциальный контраст:** каждый канал в степени 1.8.
6. **Нормализация вектора:** каналы делятся на максимум из трёх — цвет бара не зависит от его
   громкости, только от соотношения полос.
7. **HSV-форсирование:** `S = 1.0`, `V = 1.0` — серый и блёклый цвет исчезают, остаются неоновые
   оттенки.
8. **Высота:** пик (`max |sample|`) блока, нормированный по самому громкому блоку трека — удары дают
   иглы, а не холмы.
9. **Отрисовка:** зеркальные бары без зазора на фоне `#141414`.

## Разрешение и баланс полос

Две правки после первого показа владельцу («перескок в красный и очень широкие полосы»).

**Разрешение.** Бар по умолчанию был 2 px: половина горизонтальной детализации уходила в никуда.
Теперь один бар = один пиксель (`--waveform-bar-width 1`), и профиль строится на всю ширину полосы.
Проверка по пикселям PNG: заполнение обязано быть одним непрерывным интервалом — 1 интервал на
1200 столбцов, как и должно быть.

**Баланс.** Даже с перцептивными весами 1.5 и 2.5 картинка уходила в красный: бас в любой записи
несёт на порядок больше энергии, чем верх, и в степени 1.8 это преимущество только усиливалось.

считается один раз при загрузке), и уже потом применяются веса, степень 1.8 и HSV-форсирование.

Порядок важен и записан в коде: выравнивание убирает физический перекос энергии, веса — то, как
слышит ухо, степень — контраст, HSV — чистоту оттенка.

## Цвет не должен зависеть от окна

Владелец заметил, что волна «пульсирует вместе с музыкой» и это путает. Причина была в том, **где**
считался цвет: он выводился в `profile()` из тех баров, что попали в текущее окно, вместе со
сглаживанием по соседям. При прокрутке каждый кадр сглаживал другой набор соседей, и вся полоса
мерцала в такт движению.

Теперь таблица цветов считается один раз при загрузке: цвет каждого столбца конверта зависит только
от его собственного баланса полос, сглаживание по двадцати пикселям применяется там же. Рендер только
усредняет цвета столбцов, попавших в бар.

Проверка в гейте: два окна одного трека (0,0–0,5 и 0,1–0,6 длительности, по 400 баров) сравниваются
по перекрывающимся моментам времени. Оттенок одного и того же момента обязан совпадать.

```
dj-ui: colour does not depend on the window (max 0,0 degrees over 320 bars)
dj-ui: colour does not depend on the window (max 0,0 degrees over 147 bars)
```

Допуск — 25 градусов, и он не «под ответ»: на разреженном материале бар может захватить тишину в
одном окне и не захватить в другом, поэтому тихие бары из сравнения исключены (сравнивать чёрный с
цветом бессмысленно). До правки проверка показывала расхождение до 255 уровней по каналам.

## Почему пульсация была видна на зуме ≈18

Цвет был ни при чём. На большом зуме баров больше, чем столбцов конверта: один столбец приходится на
несколько баров. В коде для такого случая стояла заглушка — брать **первый столбец окна**. В
результате все бары видимой полосы показывали один и тот же столбец, и вся волна несла амплитуду
одного столбца. При воспроизведении окно едет, столбец под ним меняется — полоса «пульсирует в такт
музыке».

Две правки:

1. **Заглушка исправлена:** бар, которому не досталось столбца, берёт столбец под своей серединой,
   а не первый в окне. Теперь разные бары показывают разное время.
2. **Разрешение конверта увеличено:** 128 кадров на столбец вместо 512 (2,7 мс при 48 кГц). На зуме
   это вчетверо больше деталей. БПФ при этом дополняется нулями до 512 отсчётов: короткий столбец
   даёт хорошее разрешение по времени, но слишком мало бинов, чтобы отличить 20 Гц от 280 Гц.

Проверка на окне 2% длительности (тот самый зум): высота заполнения по барам теперь разная —
126, 102, 52, 32, 24, 12, 8, 6, 2, 1 пикселей, — а не одно число на всю ширину.

Цвет по-прежнему берётся из таблицы, посчитанной один раз при загрузке, поэтому от окна не зависит;
это отдельно проверяется в гейте (`colour does not depend on the window`).

### Два разрешения: амплитуда короткая, полосы длинная

Увеличение разрешения конверта до 128 кадров сразу вскрыло две вещи.

**Полосы при коротком окне считать нельзя.** При 128 отсчётах разрешение по частоте — 375 Гц: полосы
«20–280» и «280–3500» физически неразличимы, тон 440 Гц читался как бас. Нулевое дополнение до 512
даёт красивые бины, но не разрешение — это подмена. Поэтому анализ теперь двухуровневый:

- **амплитуда** столбца — по короткому окну 128 отсчётов (2,7 мс): удары остаются иглами;
- **полосы** — по окну 1024 отсчёта (21 мс), перекрывающемуся на 7/8: разрешение 47 Гц, бас снова
  отличим от середины.

Окно Ханна при этом накладывается на **данные**, а не на дополненную длину: иначе данные попадают под
нарастающую четверть окна, спектр заваливается в бас, и 440 Гц читается как низ.

**Проверка:** `bands low 0,080 mid 0,148 high 0,000` на тоне 440 Гц — середина ведущая, как и должно
быть. До правки было `low 0,200 mid 0,096`.

### Почему упала проверка загрузки

Пока разрешение было крупным, анализ укладывался в один снапшот, и гонка не проявлялась. С мелким
разрешением загрузка занимает ~600 мс, и выяснилось, что проверка читала состояние деки через
`toString()`: у枚举 serde это либо строка (`"Ready"`), либо объект с одним ключом
(`{"Loading":{"progress":0}}`). Строка читалась верно, объект — как пустая строка, поэтому первый же
снапшот «Loading» считался готовностью. Теперь разбираются обе формы, «Failed» показывает сообщение
движка, а «Loading» честно ждёт.

## Поля за пределами трека

Владелец заметил: после паузы и загрузки другой композиции пустые места **слева** от начала
заполняются странным цветом, похожим на кусок предыдущей волны.

Причина: бары, попадавшие за границы трека, прижимались к крайнему столбцу конверта и рисовались его
цветом поверх области «вне трека». Область рисовалась правильным цветом (`--waveform-outside-color`),
но бары её перекрывали.

Теперь `profile()` помечает такие бары флагом `outside`, а рендер (и QML, и PNG) их пропускает: за
пределами трека остаётся сплошной цвет полосы.

Проверка по пикселям: окно, начинающееся **до** трека (`--waveform-span "-0.10,0.30"`), в первой
четверти даёт ровно один цвет — фон `#141414`, — а внутри трека 17 различных цветов. До правки в этой
четверти были цвета волны.

Заодно `clear()` теперь очищает и таблицу цветов: после выгрузки деки в памяти не остаётся цветов
предыдущего трека.

## Муар на общем виде

Владелец снова увидел пиксельный муар — теперь на масштабе 1:1, где виден весь трек.

Причина не в цвете: при таком масштабе один бар покрывает несколько столбцов конверта, и пик внутри
каждого столбца скачет. Соседние бары отличаются на пиксель-два даже там, где музыка ровная, и эта
регулярная рябь читается как муар по всей полосе.

Лечение — то, что и предложил владелец: **горизонтальное размытие**, но привязанное к масштабу.

- Если бар покрывает больше 1,5 столбца (общий вид), амплитуды соседних баров сглаживаются гауссом:
  радиус `ceil(columnsPerBar / 2)`, но не больше 4, σ ≈ 0,45 × columnsPerBar.
- Если бар покрывает меньше (зум), сглаживание не применяется: транзиенты и удары остаются иглами.

### Измерение

Шероховатость считается как среднее расстояние бара до среднего из соседей, в пикселях:

| Вид | Было | Стало |
|---|---|---|
| весь трек (1200 баров) | 1,45 px | 0,39 px |
| зум 2% | — | 0,13 px |

Число печатает и сам рендер (`dj-ui: roughness`), и проверка в гейте: на общем виде она падает, если
шероховатость больше 1 px. «Зернисто» — это не то, что гейт может прочитать; пиксели — может.

## Сглаживание, которое не пульсирует

Первая попытка сгладить общий вид сделала хуже: появились «новые волны» и пульсация. Причина —
радиус сглаживания считался от того, **сколько столбцов приходится на текущий бар**, а это число
меняется, пока окно едет. Каждый кадр сглаживание было другим, и полоса дышала.

Правильный способ — привязать сглаживание к **масштабу**, а не к окну:

- при загрузке считаются готовые «рампы» пиков по столбцам для фиксированного набора радиусов —
  0, 2, 4, 8 и 16 столбцов;
- при отрисовке выбирается рампа по числу столбцов на бар (не меньше двух радиусов на бар), и бар
  берёт среднее по покрытым столбцам. Для зума, где бар ≤ 1,5 столбца, берётся рампа 0 — без
  сглаживания, транзиенты остаются иглами.

Так радиус зависит только от зума: при прокрутке он не меняется, и пульсации нет по построению.

### Измерения

| Вид | Шероховатость |
|---|---|
| весь трек | 0,24 px |
| зум 2% | 0,13 px |

Независимость от окна теперь проверяется и по высоте, а не только по цвету: два окна одного трека
(0,0–0,5 и 0,1–0,6) сравниваются в совпадающих моментах.

```
dj-ui: the picture does not depend on the window (max 0,0 degrees, 0,000 of height, over 320 bars)
dj-ui: the picture does not depend on the window (max 0,2 degrees, 0,001 of height, over 109 bars)
```

Допуск по высоте — 0,04 полной шкалы; до правки расхождение доходило до 0,207, и это была та самая
пульсация. Проверка теперь ловит её автоматически, а не по ощущению.

## Остаточные волны на общем виде

После привязки сглаживания к масштабу на общем виде оставалась лёгкая волна. Проверил на материале,
где волн быть не должно: 120 секунд розового шума — статистически самый ровный сигнал, который есть.
Конверт получился 45 000 столбцов, как у настоящего трека.

| Что меряем | Было (радиус 2 бара) | Стало (8 баров) |
|---|---|---|
| разброс высоты по полосе | 7,5 px | **1,6 px** |
| медленная волна (средние по 40 баров) | 9,0 px | **1,6 px** |
| высота полосы | 33 px | 33 px |

То есть на ровном материале полоса теперь плоская с точностью 5%. Радиус сглаживания — «восемь
баров» в столбцах конверта, по-прежнему только от зума.

## Частота кадров при быстром скольжении

Ощущение низкой частоты кадров на зуме складывалось из двух причин, и обе измерены.

**1. Полоса рисовалась в QML Canvas.** На каждый кадр — 1200 `QVariantMap` из C++ в JavaScript,
затем три `fillRect` на бар через `Qt.rgba`. Отрисовка перенесена в C++: `WaveformItem`
(`QQuickPaintedItem`) поверх `Waveform::bars()` — плоские структуры, без QVariant и без переходов в
JavaScript.

```
dj-ui: frame cost p50 0,78 ms, p99 0,96 ms, max 1,05 ms over 60 frames   (конверт 30 000 столбцов)
```

Бюджет кадра при 60 Гц — 16,7 мс; отрисовка полосы занимает 6% бюджета. Гейт падает, если p99
превышает 8 мс (половина бюджета): тогда частоту кадров задаёт полоса, а не дисплей.

**2. Движок публикует состояние 20 раз в секунду.** Это правильная частота для чисел и слишком
грубая для полосы, которая едет под плейхедом: на зуме 18× шаг в 50 мс виден как рывки. UI теперь
проецирует позицию между снапшотами — по своему sample rate и текущему темпу — с частотой 16 мс, а
каждый новый снапшот ставит её обратно на число движка. Картинка двигается каждый кадр и при этом не
может уехать от звука.

## Резкость на большом зуме

Владелец: «при большом зуме слишком сглажена, биты не идентифицировать».

Причина — правило сглаживания. Оно выбирало радиус по числу столбцов конверта на бар, а это число
растёт с зумом: на 10× для пятиминутного трека один бар покрывает 50 мс музыки, и радиус в два бара
(100 мс) сглаживал ровно тот удар, который человек ищет глазами.

Теперь выбор делается **во времени**, а не в столбцах:

- весь трек (span ≥ 0,9) — сглаживание всегда: там зерно в один пиксель на бар это шум, а не музыка;
- зум — сглаживание только если бар всё ещё покрывает длинный кусок (> 200 мс); иначе высота бара —
  максимум по его столбцам, без усреднений и без рамп.

Замер на барабанах (окно начинается на 0,3 трека):

| Окно | Было | Стало |
|---|---|---|
| 2,4 с (span 0,3) | 12 пиков, средний спад 3,8 px | **13 пиков, спад 9,9 px** |
| 0,8 с (span 0,1) | 0,38 px шероховатости | 0,38 px |
| весь трек | 0,04 px | 0,10 px — по-прежнему гладко |

В гейт добавлена проверка: в `--self-check` считается шероховатость обзора и зума, и прогон падает,
если зум такой же плоский, как обзор.

```
dj-ui: overview roughness 0,04 px
dj-ui: zoomed roughness 0,38 px (overview 0,04)
```

## Сглаживание по величине зума и предел 100×

Владелец: «степень сглаживания надо включать в зависимости от величины зума; на высоких зумах нормально,
на низких опять муар», и «максимальный зум сделать 100».

Сглаживание перестало быть выключателем. Его вес задаётся шириной окна:

```
weight = clamp((span - 0.35) / 0.55, 0, 1)      span — доля трека в окне
```

весь трек (span 1,0) — вес 1, зум 3× и глубже — вес 0, между ними рампа вводится постепенно, так что
каждый шаг колеса меняет степень сглаживания, а не переключает её.

Второе изменение: высота бара ниже обзора — **среднее** по столбцам, которые бар покрывает, а не
максимум. Максимум выбирал самый громкий столбец из многих, и при движении сетки бара относительно сетки
столбцов победитель прыгал от бара к бару — это и был муар.

Замер на 180-секундном треке (120 BPM, бочка, снейр, хэты, бас), окно начинается на 0,4 трека.
Шероховатость — средний модуль второй разности высот, делённый на высоту полосы; «рябь» — сильнейшая
нормированная автокорреляция в полосе 3…60 px.

| Окно | Зум | Шероховатость было | стало | Рябь было | стало |
|---|---|---|---|---|---|
| весь трек | 1× | 0,112 | 0,113 | 0,923 | 0,923 |
| 0,7 | 1,4× | 0,263 | **0,131** | 0,935 | 0,931 |
| 0,5 | 2× | 0,246 | **0,135** | 0,966 | **0,788** |
| 0,2 | 5× | 0,104 | **0,067** | 0,929 | 0,859 |
| 0,1 | 10× | — | 0,037 | — | 0,824 |
| 0,01 | 100× | — | 0,012 | — | 0,762 |

На низких зумах зерно вдвое меньше, обзор не изменился, глубокий зум остался иглами.

Высота нормируется по уровню зума (максимум рампы этого уровня), а не по видимому окну: нормировка по
окну делала высоту зависимой от прокрутки — `--self-check` такое отвергает («height depends on the
window»).

Предел зума: `UiSettings.waveformZoom` 1…100 (по умолчанию 10), колесо упирается в 0,01 → 100×.

```
dj-ui: deck A opens at 100,0x zoom (wanted 100,0x)
dj-ui: the wheel reaches 100,0x zoom
```

## Больше сглаживания на всех уровнях, зум до 400×

Владелец: «вижу муар на всех уровнях; надо абсолютное значение сглаживания везде увеличить, с
сохранением градации по уровням», и добавить зум 200 и 400.

Что сделано:

- радиусы рампы удвоены: `{0, 2, 4, 8, 16, 32}` → `{1, 4, 8, 16, 32, 64}` столбцов;
- самый младший уровень — не «без сглаживания», а **радиус 1**: на самом глубоком зуме это превращает
  ступеньки конверта в наклон вместо гребёнки из одинаковых по высоте полос;
- вес сглаживания больше не падает до нуля: `clamp(0.5 + 0.5·(span − 0.05)/0.85, 0.5, 1.0)` — градация
  сохранена (глубокий зум 0,5, весь трек 1,0), но нижняя граница поднята;
- `waveformZoom` и колесо — до 400× (`zoomSpan` до 0,0025).

Шероховатость (средний модуль второй разности высот к высоте полосы), 180-секундный трек, окно с 0,4:

| Зум | Было | Стало |
|---|---|---|
| 1× | 0,113 | **0,085** |
| 2× | 0,135 | **0,075** |
| 5× | 0,067 | **0,047** |
| 10× | 0,037 | **0,031** |
| 20× | 0,020 | 0,018 |
| 100× | 0,012 | 0,011 |

Биты при этом читаются: средний спад после пика 5,8–6,6 px на зумах 2–10×.

```
dj-ui: deck A opens at 10,0x zoom (wanted 10,0x)
dj-ui: the wheel reaches 400,0x zoom
dj-ui: overview roughness 0,03 px
dj-ui: zoomed roughness 0,31 px (overview 0,03)
```

Предел на 200–400× — разрешение конверта: столбец 128 кадров (2,7 мс), на 400× это около семи баров
на столбец, полоса показывает «envelope limit». Мельче — 32 кадра на столбец (вчетверо больший кэш).

## Средне до 15×, сильнее выше

Владелец: «Надо усилить сглаживание: 1) до 15× — средне; 2) после 15× — чем выше, тем сильнее».

Правило задано в зумах, а не в ширине окна:

```
heat(zoom) = 1                                  при zoom <= 15
           = 1 + 3·log(zoom/15)/log(400/15)     выше 15, до 4 на 400×
```

- радиус рампы = 8 · (столбцов на бар) · heat;
- вес смешивания = средний по окну + 0,25·(heat − 1), не больше 1.

До 15× числа не изменились — это и есть «средне». Выше 15× сглаживание растёт плавно, без обрыва:
15× даёт heat 1, 100× — 2,7, 400× — 4.

Замер, 180-секундный трек, окно с 0,4. Шероховатость — средний модуль второй разности высот к высоте
полосы; `rough/std` — та же величина к разбросу высот в окне (показывает, сколько остаётся мелкого
дрожания при той же общей форме):

| Зум | Шероховатость | rough/std |
|---|---|---|
| 1× | 0,085 | 0,257 |
| 5× | 0,047 | 0,302 |
| 10× | 0,031 | 0,216 |
| 15× | 0,023 | 0,149 |
| 20× | 0,017 | 0,119 |
| 100× | 0,005 | 0,024 |
| 200× | 0,002 | 0,014 |
| 400× | 0,001 | 0,006 |

Общая форма при этом сохраняется: разброс высот 0,15–0,33 на всех уровнях — сглаживается дрожание, а
не рисунок трека.

```
dj-ui: overview roughness 0,03 px
dj-ui: zoomed roughness 0,21 px (overview 0,03)
```

## Нарастание сглаживания после 15× приторможено

Владелец: «После 40× при увеличении сглаживание становится слишком сильным».

Кривая роста заменена на насыщающуюся:

```
heat(zoom) = 1                                          при zoom <= 15
           = 1 + 1.5·(zoom/15 − 1)/((zoom/15 − 1) + 2)  выше 15, потолок 2,5
```

Было `1 + 3·log(zoom/15)/log(400/15)` (до 4 на 400×). Стало: 1,2 на 20×, 1,7 на 40×, 2,1 на 100×,
2,4 на 400×. Последнее десятикратие зума добавляет примерно десятую часть того, что добавило первое.

| Зум | rough/std было | стало |
|---|---|---|
| 15× | 0,149 | 0,149 |
| 20× | 0,119 | 0,121 |
| 100× | 0,024 | **0,038** |
| 200× | 0,014 | **0,018** |
| 400× | 0,006 | **0,008** |

До 15× не изменилось ничего, на глубоком зуме сглаживания меньше — ровно там, где оно мешало.
Разброс высот 0,14–0,18 на всей лестнице: рисунок не размыт, уходит только дрожание.

## После 200× размытие снижается

Владелец: «После 200× надо снизить размытие».

Две правки, обе начинаются на 200× и обе плавные:

- соседство рампы сужается с восьми баров до четырёх к 400× (на 200–400× окно содержит всего десятки
  столбцов конверта, и восемь баров — это почти вся картинка);
- heat после 200× не растёт, а спадает: 2,3 на 200× → 1,1 на 400×.

Плюс вес смешивания больше не доходит до единицы: потолок 0,9 — иначе в полосе остаётся только
сглаженная рампа и от собственной формы трека ничего.

| Зум | rough/std было | стало |
|---|---|---|
| 100× | 0,038 | 0,038 |
| 200× | 0,018 | 0,018 |
| 303× | — | 0,019 |
| 400× | 0,008 | **0,022** |

На 400× детали втрое больше, переход 200→400 идёт без ступеньки (0,018 → 0,019 → 0,022). Разброс высот
0,13–0,17: форма трека на месте.
