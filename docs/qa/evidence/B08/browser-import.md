# B08 · Добавление файлов в коллекцию из браузера

Выделение строк, контекстное меню, подтверждение, прогресс и вопрос о дубле. Работу делает движок,
оболочка только говорит, что выбрано.

## Что проверено

| Проверка | Результат |
|---|---|
| пачка из двух одинаковых записей | первый файл лёг, на втором пачка встала с вопросом |
| вопрос | `agreement > 0.9`, две разные копии одной записи, формат назван |
| ответ «Добавить с меткой» | обе копии в коллекции, `placed 2`, `done 2`, `failed 0`, `running false` |
| остановка | `cancel` до первого файла — `done 0`, `placed 0`, коллекция пуста |
| оболочка | `--smoke`: `QML scene loaded, no Qt warnings`, истории браузера проходят |
| выделение Ctrl | две строки выбраны, окно говорит «2 item(s) selected» |
| окно прогресса | видно во время пачки: «0 of 2 added, 0 skipped, 0 failed» |
| окно дубля | обе копии с числами: `WAV · lossless · 48.0 kHz · 768 kbps · 0:20 · 1.8 MB` |
| «Добавить с меткой» | `2 of 2, 2 placed, 0 skipped, 0 failed`, в коллекции два файла |
| один файл | окна подтверждения нет, пачка идёт, ответ «Пропустить» ничего не добавляет |
| колонки коллекции | строка модели `A \| Track \| 20000 ms`, на экране `"A"` и `0:20`, шапка `Исполнитель` |
| имена в записи | `dj-library/tests/import.rs`: `tags.artist`/`tags.album`/`tags.title` в `.djmeta` после импорта |
| дописывание имён при загрузке | файл из коллекции владельца: `.djmeta` получил `tags {artist "Waka Flocka Flame", album "Mr. Miyagi (feat. Waka Flocka Flame)", title …}`, `key 8d`, `bpm 136.99` |
| анализ при импорте | реальный трек 2:22 → строка `Waka Flocka Flame \| Mr. Miyagi … \| 142315 ms \| 137.0 BPM \| 8d` |
| метаданные исходника | `the_metadata_beside_the_source_travels_with_the_copy`: сетка 128 BPM и `8m` переехали в запись копии |
| колонки: порядок и ширина | `key` первым, ширина artist 0,22 → 0,27; на экране ячейка artist уехала вправо; в layout-файле `collection_columns[0].id = key`, `[1].width = 0.27` |
| ширина мышью | настоящие события в шапке: край artist 0,22 → 0,25 |
| переезд колонки | после переезда строка читается (`Track`), таблица не пустеет |
| перезапуск | второй `LayoutSettings` читает тот же файл: `key` первым, artist 0,27 |
| файлы после загрузки из коллекции | загрузка идёт через мост (`bridge.load`), после неё `showFiles()` возвращает тот же каталог; файл сессии пуст |
| старая сессия с папкой коллекции | старт говорит «inside the collection; the file list opens in /home/hermes» и открывает музыкальную папку |
| курсор коллекции | после визита в файлы вернулся на строку 1 из 1 |
| курсор файлов | после визита в коллекцию вернулся на строку 1 из 1 |
| курсоры в сессии | запись и чтение сессии вернули обе строки |
| параллельный анализ | `parallel_analysis_takes_several_files_at_once`: пик одновременных анализов > 1 |
| без флага | `without_parallel_the_analysis_is_one_file_at_a_time`: пик ровно 1 |
| файл без тегов | `Shadow Rhythm - Aura of Oresa - Treblo.flac` — теги пусты, запись имён не пишется; строка покажет исполнителя и название из имени файла |

Тесты: `apps/dj-engine/tests/import.rs` — `a_duplicate_is_asked_about_and_the_answer_is_obeyed`,
`a_stopped_batch_takes_no_more_files`.

Сквозная проверка оболочки: `scripts/ui.sh --engine-check` запускает
`dj-ui --connect SOCKET --collection-root ROOT --import-check --import-fixture TRACK` на живом
движке и настоящем треке (двадцать секунд, скопирован дважды): выделяет две строки, читает окно
подтверждения, ждёт окно прогресса и окно дубля, нажимает «Добавить с меткой», считает файлы в
коллекции, затем повторяет с одним файлом и отвечает «Пропустить».

Отпечаток трёхсекундного файла пуст, поэтому проверка берёт двадцатисекундный: копию, которую
никто не узнал, нельзя и спросить.

## Чего нет

- `parallel` принимается протоколом, но пачка идёт по одному файлу: вопрос о дубле всё равно её
  останавливает. Многопоточный импорт — отдельная работа с очередью из `MEDIA-007`.
- Окно вопроса не умеет «так же для всех остальных»: каждый дубль спрашивается отдельно.
- Проверка не нажимает правую кнопку мышью: она зовёт ту же функцию, что и меню (`askImport`).
  Само меню — `Menu` с одним пунктом, его открытие проверяется глазами, а не событием.

## Анализ из коллекции: окно прогресса и чекбокс параллельности

**Запрос владельца.** «В коллекции при выборе `Analyze...` нужно выдавать окошко с прогрессом. Иначе
совсем непонятно что происходит. И если выбрано несколько композиций — выдавать окошко с чекбоксом
параллельной обработки и прогрессом.»

**Что было.** `Analyze…` отправлял по одной команде `AnalyzeTrack` на каждый файл и ничего не
показывал: ни числа, ни текущего файла, ни признака, что работа идёт. Список перечитывался таймером
на 20 с «на удачу».

**Что стало.** Команда `AnalyzeTracks { paths, parallel }` и состояние `AnalyzeState` в снапшоте
(`analysis`). Один трек — сразу окно прогресса; несколько — окно подтверждения с галочкой, затем то же
окно прогресса. Отмена — `AnalyzeCancel`, между файлами.

**Замер (`--analyze-check`, три копии 64-секундной бит-фикстуры без метаданных):**

```
dj-ui: one track: progress window, 0 of 1
dj-ui: three tracks: confirmation with the parallel box, starting
dj-ui: batch: progress window, 0 of 3
dj-ui: rows with a tempo after the batch: 3 of 3
dj-ui: analyze check done
```

**Грабли, купленные прогонами:**

- **Чистый синус доли не даёт.** Первая версия проверки брала тот же 20-секундный тон, что и импорт:
  у него нет онсетов, темп не измеряется, и «строки с темпом» остаются нулём — проверка падала не на
  окнах, а на фикстуре. Нужен бит и не короче сорокасекундного окна, в котором детектор голосует:
  восемь секунд `drums-8s` склеены в 64 секунды через `ffmpeg -stream_loop`.
- **`id` чекбокса не виден из футера диалога.** `checked: analyzeParallelBox.checked` в обработчике
  кнопки дал `ReferenceError: analyzeParallelBox is not defined` — окно закрывалось, команда не
  уходила, и проверка видела старое состояние (`done 1 of 1`). Выбор хранится в свойстве самого
  диалога (`analyzeDialog.parallel`), которое видно обеим сторонам.
- **Окно прогресса для одного файла может мелькнуть.** Проверка ловит его опросом каждые 10 мс;
  на 64-секундном файле анализ идёт секунды, и окно успевает быть видимым.

## Сортировка коллекции и порядок разделов

**Запрос владельца.** «При нажатии на колонку без `Shift` — сортировка по этой колонке. При нажатии с
`Shift`, если ещё есть сортировка по другой колонке, по данной идёт вторичная сортировка.» И:
«`Collection` нужно разместить в самом верху левой панели, `Files` — в самом низу.»

**Что стало.** Сортировка живёт в `FileBrowser` (`sortCollection(column, shift)`, `collectionSort`),
шапка сортирует по щелчку с настоящей мышью, метка в шапке показывает ключ (▲/▼ — решающий,
△/▽ — следующий). Рельс разбит на два списка: `Collection` и `Playlists` сверху, `Files` снизу.

**Замер (`--sort-check`, четыре копии бит-фикстуры, имена `<Исполнитель> - <Название>`):**

```
dj-ui: rail: Collection at 13,0, Files at 55,0
dj-ui: click artist -> Alpha - Apple | Alpha - Zebra | Beta - Apple | Gamma - Mango
dj-ui: click artist again -> Gamma - Mango | Beta - Apple | Alpha - Apple | Alpha - Zebra
dj-ui: click title -> Alpha - Apple | Beta - Apple | Gamma - Mango | Alpha - Zebra
dj-ui: click title again -> Alpha - Zebra | Gamma - Mango | Alpha - Apple | Beta - Apple
dj-ui: shift click artist -> Alpha - Zebra | Gamma - Mango | Alpha - Apple | Beta - Apple
dj-ui: shift click artist again -> Alpha - Zebra | Gamma - Mango | Beta - Apple | Alpha - Apple
dj-ui: sort check done
```

**Грабли:**

- **Шапка не имеет ширины, пока оболочка не разложилась.** Первый заход щёлкал в точку (0, 0): там
  край первой колонки, и жест читался как изменение ширины, а не как щелчок по названию. Проверка ждёт
  `header->width() > 1` перед прицеливанием.
- **Равные ключи держат порядок имён,** поэтому «Shift по артисту» на уже отсортированном по названию
  списке ничего не меняет — проверка переворачивает второй ключ вторым Shift, иначе она ничего не
  доказывает.
- **Пустые ячейки внизу при любом направлении** — иначе трек без BPM оказывается «самым быстрым».

## Сортировка по тональности: вторичный ключ работает

**Вопрос владельца.** «Поле `Key` при вторичной сортировке, похоже, не учитывается.»

**Замер.** В `--sort-check` появились записи `.djmeta` с тональностями: `Alpha - Zebra` — `2d`,
`Gamma - Mango` — `8d`, `Beta - Apple` — `8m`, `Alpha - Apple` — `10d`.

```
dj-ui: click key -> Alpha - Zebra | Gamma - Mango | Beta - Apple | Alpha - Apple
dj-ui: artist then shift key -> Alpha - Zebra | Alpha - Apple | Beta - Apple | Gamma - Mango
```

Первый порядок — квинтовый круг (`2d`, `8d`, `8m`, `10d`), а не текст (текст дал бы `10d`, `2d`, `8d`,
`8m`). Второй — артист решает группы, тональность решает внутри `Alpha`: `2d` раньше `10d`.

**Что нашлось и исправлено.** `camelot()` принимал только строчные `d`/`m` и не знал камелотной записи:
ключ `8D` или `8A` не разбирался и сравнивался как текст, а текст ставит `10d` перед `2d` — ровно
симптом «поле не учитывается». Теперь принимаются `d`/`m` и `A`/`B` в любом регистре, номер ограничен
1…12; неразборчивая запись по-прежнему сравнивается текстом.

**Что проверить у себя, если порядок всё ещё не тот:** вторичный ключ решает только между строками, где
первый ключ совпал (по уникальному артисту разницы не будет), а строки без тональности стоят внизу при
любом направлении.
