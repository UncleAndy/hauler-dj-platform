# RT-приоритет звукового потока (ADR-0010)

Решение: **приоритет выдаёт упаковка, приложение только проверяет и предупреждает.** Приложение
не просит привилегий и не пытается стать real-time само — на чужой системе это лишний отказ, а на
своей лишняя зависимость от брокера.

## Зачем

Замер A05 (15 минут, петля 2 с, 48 кГц / 256 кадров): стоимость графа — 6 мкс медиана и 81 мкс
максимум, то есть 1,5 % периода. И при этом 3323 невольных переключения контекста за прогон,
635 мс суммарной задержки в очереди и максимальный интервал колбэка 14,6 мс — 2,74 периода. Поток
снимали с процессора в среднем 191 мкс за раз, и один раз — почти на три периода.

Вывод: на обычном десктопе `SCHED_OTHER` для звука недостаточно, и это не лечится оптимизацией
кода.

## Linux: юнит с RT-политикой

Приложение не запускает себя само; его запускает юнит. Для пользовательского юнита:

```ini
[Service]
# 20–30 хватает: выше 50 бессмысленно и вредно для системных задач
CPUSchedulingPolicy=fifo
CPUSchedulingPriority=20
# Только если звук не нужен в фоне:
# Nice=-10
```

NixOS: то же самое через `systemd.user.services.<name>.serviceConfig`, плюс `security.rtkit.enable`
для тех компонентов, которые берут приоритет через брокера (PipeWire делает это сам).

Проверить, что приоритет действительно выдан, можно без нашего кода:

```
systemd-run --user --scope -p CPUSchedulingPolicy=fifo -p CPUSchedulingPriority=20 \
  cargo run --release -p dj-live-probe -- --seconds 60 --loop-seconds 2
```

В отчёте при этом должно быть `thread_scheduling.policy = "fifo"` и `realtime = true`.

## Что делает приложение

- читает политику потока колбэка из procfs и кладёт в отчёт (`thread_scheduling`);
- выводит вердикт `realtime` (`true`/`false`) и, если `false`, — текст с указанием, что именно
  нужно поправить;
- пишет предупреждение в stderr при старте, чтобы «тихо работает без приоритета» не стало нормой.

## Windows и macOS (R1)

- Windows: MMCSS, `AvSetMmThreadCharacteristics("Pro Audio")` — ставится драйвером потока в
  приложении, потому что иного механизма нет.
- macOS: `thread_policy_set` с `THREAD_TIME_CONSTRAINT_POLICY` для аудиопотока.
- Обе платформы получат это вместе с первым релизом под них; до тех пор проверка сообщает
  `policy = "unknown"` и не делает вид, что всё в порядке.

## Чего приложение не обещает

Ноль xrun'ов на произвольной машине. Вердикт DJP-NFR-004 относится к зафиксированному стенду
(CPU, governor, kernel, audio server, устройство, нагрузка) и выносится по счётчику xrun, который
ещё предстоит сделать: сейчас мы считаем только свою сторону и провал устройства не увидим.
