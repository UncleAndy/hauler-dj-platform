# Порт Hauler DJ под Windows — план

Дата: 2026-11-18. Основание: указание владельца — полное портирование, Linux-версия не меняется, включая
процедуры сборки готовых exe движка и GUI. Проверок под Windows не делаем, отдельного гейта нет: хост — NixOS.

## 0. Границы

- **Linux-версия не меняется.** Всё платформенное — за `cfg(target_os = "windows")` или фичами по
  платформе. Linux-путь (unix-сокет, pipewire, XDG-каталоги) остаётся байт в байт прежним.
- **Проверок под Windows нет.** Приёмка этапа — компиляция в `.exe` и запуск `--help`; отдельного гейта не
  заводим. Существующий `scripts/check.sh` остаётся единственным и должен быть зелёным после каждого этапа —
  это текущая дисциплина проекта, а не новый гейт.
- **Установщик (MSI/Inno) — вне первой версии:** отдаём zip с готовой папкой.

## 1. Что уже переносимо (проверено по коду, не по общим словам)

- Rust: 63,6 тыс. строк, один workspace. Зависимости переносимые: `symphonia` (чистый Rust), `rusqlite` с
  `bundled` (C-часть собирается mingw-ом), `ort` с `load-dynamic` (ONNX Runtime грузится в рантайме — на
  Windows достаточно положить `onnxruntime.dll`), `cpal` (WASAPI из коробки).
- Протокол движок↔оболочка — JSON-строки поверх потока; транспорт ровно один, `crates/dj-bridge`
  (363 строки). Вся платформенность — там.
- В коде **нет ни одного** `cfg(target_os)` — платформенного долга нет, но и ни одна строка не собиралась под
  Windows.
- Qt 6 Quick + CMake: сам по себе переносим; в репозитории только Nix-сборка.
- Файлового наблюдателя (`notify`) нет — платформенных сюрпризов меньше.
- Оболочка и движок — **два процесса**: их можно собирать разными тулчейнами и класть рядом двумя exe; связь
  только через трубу.

## 2. Три решения

### 2.1 Транспорт — named pipe
- Windows: `\\.\pipe\hauler-dj-engine-<пользователь>`, чтобы два DJ-я не сталкивались.
- В `dj-bridge` появляется трейт `Endpoint` (listen/accept/connect) и две реализации: `std::os::unix`
  (код переезжает как есть) и named pipe через `windows-sys` (`CreateNamedPipeW`/`ConnectNamedPipe`) — без
  токио и без лишних крейтов.
- Фрейминг по строкам не трогаем: он общий для обеих платформ.
- `--socket` принимает и путь, и имя канала; по умолчанию Linux — `/tmp/hauler-dj-engine.sock` (как сейчас),
  Windows — имя канала.

### 2.2 Звук — cpal + WASAPI
- Фича `pipewire` у `cpal` переезжает в `[target.'cfg(target_os = "linux")'.dependencies]`; на Windows —
  дефолтные фичи (WASAPI).
- В `dj-audio-io` правятся только ветки перечисления устройств и выбора устройства по умолчанию.
- MMCSS (приоритет аудиопотока) — **не** в первой версии: сначала «играет». Это отдельный пункт перед релизом,
  не часть порта.

### 2.3 Тулчейны
- **Движок:** `x86_64-pc-windows-gnu`, mingw-w64 из nixpkgs (`pkgsCross.mingwW64`). Причины: не нужны ни MSVC,
  ни wine при сборке; `rusqlite/bundled` собирается mingw-ом; `ort` линковать не нужно (грузится в рантайме).
- **Оболочка:** Qt 6 под mingw — MXE (`qt6base`, `qt6declarative`, `qt6shadertools`), обёрнутый в деривацию
  `flake.nix` и закэшированный в `/nix/store`. Первая сборка MXE — часы, дальше из кэша. Вариант «собирать на
  MSVC-раннере» отклонён: хост — NixOS.
- CMake: `cmake/toolchain-mingw64.cmake` + `CMAKE_PREFIX_PATH` на Qt из MXE.

## 3. Этапы

**Э0. Скелет сборки (0,5 дня).** `flake.nix`: деривации `mxe-qt6`, `dj-engine-windows`, `dj-ui-windows`;
`scripts/windows.sh` с командами `--engine`, `--ui`, `--dist`, `--all`. Кода не касается.

**Э1. Каталоги и пути (1 день).** Новый маленький крейт `dj-paths`: один вход на каталоги (данные, конфиг,
кэш, модели). Linux — XDG как сейчас; Windows — `%APPDATA%`/`%LOCALAPPDATA%`. Заменяются 15 мест, где сейчас
руками читается `HOME`/`XDG_*`. Linux-поведение не меняется.

**Э2. Транспорт (1–2 дня).** Трейт `Endpoint` в `dj-bridge`, две реализации, значения по умолчанию по
платформе, правки в `dj-engine` (`--socket`) и `dj-ui` (`--connect`).

**Э3. Звук (1 день).** Фичи `cpal` по платформам, перечисление устройств и default под Windows, сборка без
pipewire.

**Э4. Модель путей в библиотеке (1–2 дня).** `volume`+`root` для `C:\`; сравнение путей с `/` и `\`; регистр —
в SQLite `LIKE` по умолчанию ASCII-регистронезависим, на Linux сейчас иначе, значит сравнение делаем явным
(своя функция/`case_sensitive_like`), чтобы Linux не поехал; имена с `:`/`?` из тегов не должны ломать раскладку.

**Э5. Сборка движка (0,5 дня).** `cargo build --release --target x86_64-pc-windows-gnu -p dj-engine`;
проверить, что `bundled` SQLite собрался; рядом кладётся `onnxruntime.dll` (по желанию — без него работает
встроенный детектор).

**Э6. Сборка GUI (2–3 дня).** MXE Qt6 в flake, toolchain-файл, CMake-пресет, `windeployqt` (или явный список
модулей) для Qt dll, `platforms/`, `qml/`, `styles/`, `imageformats/`; `qt.conf`; шрифты и тема.

**Э7. Дистрибутив (0,5–1 день).** `dist/windows/`: `dj-engine.exe`, `dj-ui.exe`, Qt-библиотеки и модули,
`onnxruntime.dll` (опция), `README.txt`, `hauler-dj.bat` (поднимает движок и оболочку); zip.

**Э8. Документация (0,5 дня).** `docs/windows.md`: команды сборки, состав дистрибутива, отличия (имя канала,
каталоги, отсутствие MMCSS и установщика, гейт только на Linux).

Порядок: Э0 → Э2 → Э1 → Э3 → Э5 (движок уже запускается на Windows) → Э4 → Э6 → Э7 → Э8.

## 4. Что не делаем

- Windows-гейт и проверки — нет.
- Установщик MSI/EXE — нет (zip).
- MMCSS-приоритет, WASAPI exclusive — после первой рабочей сборки.
- Прогоны под wine как приёмка — только если wine уже есть в store; иначе приёмка этапа = компиляция.

## 5. Риски и чем снимаем

1. **MXE Qt6 может не собраться с первого раза** (долгая сборка). Снимаем: отдельная деривация, фиксация
   версии Qt, кэш в store; запасной путь — собрать Qt тем же MXE один раз вручную и положить в store.
2. **`bundled` SQLite под mingw** иногда требует явного `CC_x86_64_pc_windows_gnu` — правится в
   `scripts/windows.sh`.
3. **Регистр и разделители путей** — самое коварное для Linux-регрессии; отсюда отдельный этап Э4 и явное
   сравнение вместо надежды на `LIKE`.
4. **cpal/WASAPI**: устройство по умолчанию и размер буфера. Первая сборка может играть с щелчками — это
   настройка, а не порт.
5. **QML-модули не попадут в дистрибутив** → пустое окно. Лечится `windeployqt`/списком модулей в
   `scripts/windows.sh` и проверкой содержимого `dist/windows/`.

## 6. Оценка

- Движок и оболочка, запускающиеся на Windows (Э0–Э3, Э5): **4–5 дней**.
- Полный дистрибутив с Qt и документацией (Э6–Э8): **3–5 дней**.
- Итого **7–10 дней**; поверх — 1–2 дня на возможные бои с MXE.
