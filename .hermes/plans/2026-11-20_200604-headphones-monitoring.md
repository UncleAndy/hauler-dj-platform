# План: прослушивание деки в наушниках (мониторинг)

> **Для Hermes:** исполнять этапами по порядку, каждый этап закрывается своим свидетелем из карты проверок
> и коммитом. Ничего из «не делаем» не трогать. Старт ничем не блокирован: решения владельца приняты
> (см. «Принятые решения»), остальные вопросы можно решать по ходу.

**Цель:** DJ слышит в наушниках отдельно выбранные деки независимо от положения фейдера канала, громкость
наушников и пропорция «мониторинг ↔ основной звук» — двумя ручками в центре микшера, а наушники при этом
могут быть отдельной парой каналов того же устройства или отдельным устройством воспроизведения.

**Что уже есть (это сильно сокращает работу):**

| Что | Где | Состояние |
|---|---|---|
| Шина `cue` в микшере | `crates/dj-mixer/src/lib.rs:106`, `cue()`, `set_cue_gain()` (279) | считается, но никто не включает |
| Метка канала «в наушники» | `ChannelSettings.cue` (`lib.rs:42`, комментарий «pre-crossfader») | поле есть, ставит его никто |
| Маршрут «шина → пара каналов» | `crates/dj-audio-io/src/lib.rs:19-64` (`RoutePlan`) | 4+ каналов → master 0/1, cue 2/3; проверено на S4 MK3 |
| Копирование шин в каналы устройства | `crates/dj-audio-io/src/lib.rs:859-884` | **уже пишет `cue` в каналы 2/3** |
| Модель маршрутов и классов устройств | `docs/adr/0005-audio-devices-and-routes.md` | принято: шины, а не устройства |

Вывод: DSP и маршрутизация на том же устройстве уже написаны. Не хватает четырёх вещей — ручек
мониторинга, включения шины из UI, выбора режима маршрута в настройках и второго потока для отдельного
устройства.

**Архитектура.** Микшер выдаёт две шины за блок: `master` и `cue`. Сигнал в наушниках — это
`gain · (mix · cue + (1 − mix) · main)`, где `mix` — ручка пропорции, `gain` — громкость наушников. Считается
это в `dj-mixer` (тестируемо без звуковой карты), а не в бэкенде. У мониторинга всегда свой выход: смешивать
его с основным нельзя по определению — тогда его слышит зал.

Два режима вывода — данные, а не код (`HeadphoneRoute` в `dj-config`):

1. `SameDevice { pair }` — отдельная пара каналов того же устройства (по умолчанию 2/3). Работает уже
   сегодня: `RoutePlan::cue` пишет туда шину. Добавляется только выбор пары и проверка, что каналов хватает.
   Устройство на 2 канала такой пары не имеет: тогда состояние честно `unavailable`, а не «почти работает».
2. `Device { name }` — отдельное устройство воспроизведения. Часы остаются у главного устройства; второй
   поток забирает сигнал наушников из главного коллбэка через кольцевой буфер без блокировок, ресемплируется
   при другой частоте и подстраивается по заполнению буфера. Внутри коллбэков ни замков, ни аллокаций.

`Auto` при первом запуске: 4+ канала — `SameDevice` 2/3, иначе `Device` не выбран и мониторинг выключен.

**Стек:** Rust 1.95 (движок, `dj-mixer`, `dj-audio-io`, `dj-config`), Qt 6 (QML, `BridgeClient`), существующий
гейт `scripts/check.sh` и стенд проверок `scripts/ui.sh` с `apps/dj-ui/src/checks/`.

**Исходники — прочитать до первой правки:**

- `crates/dj-mixer/src/lib.rs` — `ChannelSettings`, `begin_block`/`finish_block`, `set_cue_gain`, `cue()`;

- `apps/dj-engine/src/main.rs:1500-1560` — открытие устройства, `RoutePlan::for_channels`;
- `crates/dj-config/src/lib.rs` — `AudioConfig` (119+), как читается и пишется файл настроек;
- `apps/dj-domain/src/lib.rs` — `DjCommand` (команды) и `Snapshot` (1756, публикация состояния);

## Этап 0. Настройки наушников как данные

**Файлы:** `crates/dj-config/src/lib.rs`, тесты там же.

1. Тест: `HeadphoneConfig::default()` даёт `mode = Auto`, `gain = 1.0`, `mix = 1.0`; запись и чтение
   сохраняют все поля; отсутствие секции в файле даёт значения по умолчанию, а не ошибку.
2. Тип:
   ```rust
   pub enum HeadphoneMode { Auto, SameDevice, Device }
   pub struct HeadphoneConfig {
       pub mode: HeadphoneMode,
       pub device: Option<String>,       // только для Device
       pub pair: Option<(usize, usize)>, // только для SameDevice; None — взять из RoutePlan
       pub gain: f32,                    // 0..2
       pub mix: f32,                     // 0..1, 1 = только мониторинг
   }
   ```
3. `AudioConfig` получает `headphones: HeadphoneConfig` (с `#[serde(default)]`, чтобы старый файл читался).
4. `cargo test -p dj-config` — зелёный.

**Свидетель:** тест читает обратно то, что записано, и старый файл без секции тоже читается.

## Этап 1. Ручки мониторинга в микшере (DSP)

**Файлы:** `crates/dj-mixer/src/lib.rs`, тесты в нём.

1. Тесты (падают):
   - `cue_mix_at_one_leaves_only_the_cued_deck`: дека A в кроссфейдере слева, B помечена `cue`; при `mix = 1`
     в буфере `cue` только материал B, в `master` — только A;
   - `cue_mix_at_zero_gives_the_main_mix`: при `mix = 0` буфер наушников повторяет `master`;
   - `cue_gain_scales_the_headphones_only`: `gain = 0` даёт тишину в наушниках и не меняет `master`;
   - `a_cued_channel_is_heard_before_its_fader`: фейдер канала на нуле, `cue` включён — сигнал в наушниках есть
     (мониторинг до фейдера и до кроссфейдера).
2. Реализация: `set_cue_mix(f32)`, `set_cue_gain` уже есть; смешение — в конце `finish_block`, после лимитера,
   чтобы наушники не отставали по времени от мастера на его задержку (в микшере уже есть `cue_delay` для этого).
3. `cargo test -p dj-mixer` — зелёный.

**Свидетель:** четыре числа из тестов: уровни A и B в обеих шинах при `mix = 1` и `mix = 0`.

## Этап 2. Включение мониторинга с канала (кнопка CUE)

**Файлы:** `apps/dj-domain/src/lib.rs` (команда), `apps/dj-engine/src/lib.rs` (применение),
`apps/dj-engine/tests/cue.rs` (новый), `apps/dj-ui/src/BridgeClient.{h,cpp}`,
`apps/dj-ui/qml/mixer/MixerPanel.qml`, `apps/dj-ui/qml/mixer/HeadphoneGlyph.qml` (новый),
`apps/dj-ui/src/checks/CueChecks.cpp` (новый), `apps/dj-ui/src/checks/DeckViewChecks.cpp` (замер),
`apps/dj-ui/CMakeLists.txt` (`QML_FILES`), `scripts/ui.sh` (флаг `--cue-check`).

1. Команда `DjCommand::SetChannelCue { deck: DeckId, on: bool }`; движок ставит `ChannelSettings.cue` на
   границе блока (как остальные параметры микшера).
2. Снимок: у каждого канала уже есть поля; добавить `cue: bool` в то, что видит UI (если его нет) и
   `headphones { mode, gain, mix, available }` в `Snapshot`.
3. QML: кнопка `cue_<deck>` — **под метром своей деки** (решение владельца, 20.11), в той нижней строке
   полосы, где уже стоит число фейдера: `[−∞] [наушники]`. Метр от этого не двигается, потому что строка была и
   остаётся одна и той же высоты, и метры дек по-прежнему кончаются на линии метра мастера (метры стоят на
   `gainLabel.top`). Значок — **нарисованный** `HeadphoneGlyph.qml`, а не символ шрифта: у моноширинного шрифта
   оболочки на Windows нет ни глифа замка, ни глифа наушников (урок замка, 20.11). Подсветка и состояние — из
   снимка, как у остальных кнопок.
4. Тест движка `apps/dj-engine/tests/cue.rs`: без устройства, прямо `render_pair`: дека B помечена, кроссфейдер
   на A → в `master` B нет (перекрёстные наводки < −60 дБ), в `cue` B есть.
5. `--cue-check` (UI): нажатие кнопки уходит в движок, снимок возвращает `cue = true`, повторное нажатие снимает.

**Свидетель:** тест движка печатает пики обеих шин: `master B -inf, cue B -6.0 dB`; `--cue-check` пишет
`dj-ui: cue on deck 2 reached the engine and came back on`; замер раскладки — метры на прежней линии, кнопка
не наезжает на число фейдера.

## Этап 3. Две ручки в центре микшера, вертикально

**Файлы:** `apps/dj-ui/qml/mixer/MixerPanel.qml`, новый `apps/dj-ui/qml/mixer/CueKnob.qml` (если `TrimKnob`
не переиспользуется как есть), `apps/dj-ui/CMakeLists.txt` (`QML_FILES`), `apps/dj-ui/src/BridgeClient.cpp`,
`apps/dj-ui/src/checks/DeckViewChecks.cpp` (замер раскладки).

Ширина центральной колонки не меняется (48 px), ручки встают одна под другой:

1. Порядок сверху вниз: ручка мастера (как сейчас) → `PHONES` (громкость наушников) → `MIX` (пропорция) →
   снап/квантайз → метр. Подписи — сбоку от ручки, а не строкой под ней: на 48 px строка подписи съедает
   высоту, которая нужна третьей ручке.
2. **Место есть** (владелец посмотрел на живую оболочку, 20.11: «места там как раз хватает на пару ручек»),
   поэтому снап/квантайз остаются на месте, ничего не переезжает: ручки 34 px, подпись сбоку, порядок
   мастер → `PHONES` → `MIX` → снап/квантайз → метр. Замер остаётся как сторож: ручки не пересекаются друг с
   другом и с метром, полоса каналов не сжимается, метры не двигаются. Расширять центр и сдвигать метры —
   нельзя (решение владельца).
3. Команды `SetCueGain(f32)` и `SetCueMix(f32)`; значения сохраняются в настройках (этап 0) и переживают
   перезапуск.
4. Замер раскладки: ручки не пересекаются с метрами и между собой, полоса каналов не сжимается ниже минимума,
   окно в минимальной ширине не обрезает микшер (сейчас в проверке есть строка «knobs end at 265 px, meter A
   starts at 238 px» — она и станет свидетелем).
5. `scripts/check.sh` — зелёный.

**Свидетель:** строка замера с новыми числами и `--layout-check` без пересечений.

## Этап 4. Отдельные каналы того же устройства

**Файлы:** `apps/dj-engine/src/main.rs` (выбор плана), `crates/dj-audio-io/src/lib.rs` (проверка пары),
`crates/dj-config` (сохранение пары), UI — выбор пары в настройках.

1. План маршрута строится не «по числу каналов», а из настроек: `master` 0/1, `cue` — выбранная пара; при
   нехватке каналов снимок честно говорит `channels = 2, separate cue unavailable`, а не молчит.
2. Тест: устройство на 4 канала с `pair = (2,3)` даёт `RoutePlan { cue: Some((2,3)) }`; устройство на 2 канала
   с тем же выбором даёт `cue: None` и причину в снимке.
3. `Auto`: 4+ канала → `SameDevice` 2/3; 2 канала → мониторинг выключен с причиной `no separate pair`.

**Свидетель:** две строки плана в журнале движка для 4- и 2-канального устройства.

## Этап 5. Режим «отдельное устройство» (второй поток)

**Файлы:** новый `crates/dj-audio-io/src/secondary.rs`, `apps/dj-engine/src/main.rs`,
`crates/dj-audio-io/src/lib.rs` (общий тип), тесты в `crates/dj-audio-io/tests/`.

1. Кольцевой буфер без блокировок (SPSC, ~250 мс) между коллбэком главного устройства и коллбэком второго;
   главный пишет сигнал наушников, второй читает.
2. Ресемплер с коэффициентом из заполнения буфера: мёртвая зона ±2 мс, пределы ±0,5 %, шаг медленный — иначе
   слышно «плавание». Часы — у главного устройства, второй поток догоняет.
3. Тест без железа: два «устройства» на 48 и 44,1 кГц, прогон 10 с модельного времени; требование — буфер не
   пустеет и не переполняется, расхождение частот уходит в ноль, сэмплы не рвутся.
4. Журнал: `headphones on "…" at 44100 Hz, drift +0.02 %, buffer 118 ms`.
5. Отказ устройства наушников не глушит основной выход: состояние `headphones_lost`, повторные попытки.

**Свидетель:** тест печатает заполнение буфера в начале и в конце прогона и число вставленных/выброшенных
сэмплов (ноль).

## Не делаем

- Режим «наушники на том же выходе, что и основной звук» — **отброшен владельцем**: зал слышал бы мониторинг,
  и смысла в таком режиме нет;
- Шину `booth` и запись/`recording` — отдельные шины ADR-0005, здесь не нужны;
- split-cue (2-канальное устройство: master в L, cue в R) — см. открытый вопрос 1;
- эквалайзер и эффекты на мониторе, «mono cue»;
- автопереключение на другое устройство при потере — только честное состояние и повторные попытки;
- расширение центральной колонки микшера и сдвиг метров — ручки стоят вертикально в её ширине, а кнопка
  наушников — в нижней строке полосы, где уже стоит число фейдера, поэтому линия метров не меняется;
- глифы наушников и замка текстом: у моноширинного шрифта на Windows их нет, только геометрия.

## Принятые решения

1. **Режим «тот же выход» отброшен** (владелец, 2026-11-20). Прежняя формулировка — ~~«наушники на том же
   выходе, что и зал, мониторинг подмешивается в основной выход»~~. Причина: в этом режиме мониторинг слышит
   зал, то есть мониторинга как отдельного канала нет. Осталось два режима: отдельная пара каналов того же
   устройства и отдельное устройство; `Auto` выбирает пару 2/3, если каналов 4 и больше.
2. **Две ручки — в центральной колонке, вертикально** (владелец, 2026-11-20): «под ручкой мастера, но
   вертикально. Это не потребует расширения центральной области микшера». Прежний вариант — ~~расширение
   колонки с 48 до 76 px и две ручки в ряд~~ — отброшен.
3. **Вертикального места хватает** (владелец, 2026-11-20: «визуально места там как раз хватает на пару
   ручек»). Прежнее опасение — ~~«запаса может не хватить, и снап/квантайз переедут над метром»~~ — снято:
   ничего не переезжает, а замер остаётся сторожем раскладки.
4. **Кнопки мониторинга — под метрами дек** (владелец, 2026-11-20): «в виде наушников лучше разместить под
   метрами под соответствующими метрами дэк». Прежняя мысль — ~~кнопка в полосе рядом с фейдером~~ — отброшена.
   Значок рисуется геометрией (`HeadphoneGlyph.qml`), а не набирается символом.

## Открытые вопросы

**Блокируют старт:** нет — решения по обоим вопросам приняты, этапы 0-2 от них не зависели.

**Можно решить позже:**

1. **Split-cue для 2-канального устройства** — нужен ли он вообще, если режим «отдельное устройство» решает ту
   же задачу. Рекомендую не делать сейчас: это ещё один режим, а 2-канальные карты у DJ — редкость.
2. **Можно ли выбрать то же устройство в режиме «отдельное устройство»** — рекомендую разрешать, но
   предупреждать словами (иначе человек получит тишину или дубль и не поймёт почему).
3. **Pre-fader или post-fader мониторинг** — рекомендую pre-fader (в этом смысл: слушать трек до того, как он
   пойдёт в зал); менять не планирую, если не скажете иначе.
