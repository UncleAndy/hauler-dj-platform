# Запускатор приложения: движок, жизненный цикл, единственный экземпляр

> **Для Hermes:** каждый этап — отдельный коммит со своим зелёным прогоном. Гейт (`bash scripts/check.sh`)
> — предусловие коммита. Свидетели этапов названы в карте проверок; этап без свидетеля не закрывается.
> Строки журнала — английские, комментарии и сообщения коммитов — русские.

## Цель

Движок и оболочка запускаются одним действием DJ и живут как одно приложение:

1. нет чёрного окна консоли на Windows;
2. движок не остаётся сиротой, если оболочка упала;
3. второй запуск не поднимает второй движок — он подключается к работающему;
4. движок сам выходит через `idle grace` после последнего клиента: «закрыл оболочку — закрылось всё», а
   перезапуск оболочки внутри этого окна мгновенный.

## Архитектура

Движок — **дочерний процесс запускатора в пользовательской сессии**. Служба не годится: у сессии 0 нет
доступа к аудиоустройствам пользователя, а `%APPDATA%` у неё свой. Различаются только механизмы:

| Задача | Windows | Linux |
| --- | --- | --- |
| Нет консоли | `windows_subsystem = "windows"` у запускатора (в релизе) | консоли нет по существу |
| Движок не переживает родителя | выход по простою (10 с) — FFI не нужен | `prctl(PR_SET_PDEATHSIG, SIGTERM)` |
| Единственный экземпляр | файл замка, открытый с `share_mode(0)` | `flock(LOCK_EX|LOCK_NB)` |
| Готовность движка | endpoint-файл + успешное подключение (TCP/Unix) | то же |
| Выход по простою | общий код движка | общий код движка |

Решение по Windows: job object отложен — он требует FFI, который здесь нечем проверить; выход по простою
даёт то же свойство (сирот не остаётся), но с задержкой в десять секунд. Это записано как открытый вопрос.

## Стек

Rust (workspace), `rustix` (`process` — только unix), `dj-paths` (endpoint и каталоги). Qt не участвует.
Никакого `windows-sys` в запускаторе: замок делается `share_mode(0)` из std.

## Исходники

- `apps/dj-launcher/` — новый бинарь `dj-launcher` (в дистрибутиве он `hauler-dj.exe`).
- `apps/dj-engine/src/main.rs` — выход по простою, флаг `--idle-exit-ms`.
- `scripts/launcher-check.sh` — свидетель этапов 1–4.
- `scripts/windows.sh` — запускатор в дистрибутиве и в MSI; `.bat` зовёт его.

## Этапы

1. **Запускатор.** Аргументы `--engine`, `--ui`, `--timeout-ms`, `--engine-only`, `--verbose`. Поднимает
   движок, ждёт endpoint подключением, поднимает оболочку, ждёт её, выходит с её кодом.
   `--engine-only` — для проверки: поднять движок, дождаться сокета, напечатать `engine ready`, выйти.
2. **Lifeline.** Unix: `pre_exec` + `prctl(PR_SET_PDEATHSIG, SIGTERM)`. Windows: выход по простою.
3. **Единственный экземпляр.** Замок: при занятом замке движок не поднимается, поднимается только оболочка.
4. **Выход по простою.** Движок: сторож раз в 500 мс; клиентов нет дольше `idle grace` (по умолчанию 10 с) и
   хотя бы один клиент был — штатная остановка. `--idle-exit-ms 0` выключает (нужен проверкам с общим
   движком).
5. **Дистрибутив.** `scripts/windows.sh`: собрать `hauler-dj.exe`, положить в `dist`, включить в MSI;
   `hauler-dj.bat` зовёт запускатор и остаётся аварийным средством.

## Карта проверок

| Проверка | Что держит |
| --- | --- |
| `launcher-check.sh` / `--engine-only` | движок поднялся, endpoint появился, запускатор вышел 0 |
| `launcher-check.sh` / lifeline | после выхода запускатора процесса `dj-engine` нет через 3 с |
| `launcher-check.sh` / single | второй запускатор при живом первом не поднимает второй движок |
| `launcher-check.sh` / idle | движок с `--idle-exit-ms 400` выходит сам после отключения клиента |
| `scripts/check.sh` | всё перечисленное в гейте |

## Открытые вопросы

- **Job object на Windows** — рекомендация: сделать следующим коммитом вместе с релизной проверкой на
  машине владельца; до тех пор сирота снимается выходом по простою.
- Автозапуск при входе (планировщик / `systemd --user`) — отложен: по умолчанию выключено, чтобы не
  оставлять невидимый фоновый процесс.
- Linux-пакет (`.tar.gz` + `.desktop` + юнит) — отдельная задача, здесь только сборка бинаря.
